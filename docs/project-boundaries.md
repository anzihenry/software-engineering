# 项目三层边界

本仓库以三层对外能力组织研发知识、GitHub 自动化和跨项目治理工具。三层是责任与产品边界，不要求目录与层一一对应；它们使用同一仓库和 Git tag 发布，自动化 manifest 另行维护兼容版本。

## 第一层：研发知识与 SKILL

| 项目 | 定义 |
| --- | --- |
| 目标 | 定义软件研发各阶段应做出的决定、最低质量要求和与风险匹配的证据 |
| 受众 | 产品、开发、评审、运维、安全角色以及协作 Agent |
| 输入 | 项目目标、约束、变更风险、运行反馈和团队实践 |
| 输出 | 生命周期基线、阶段 workflow、SKILL、交付模板、演练、编码规范和内容治理规则 |
| 写权限 | 不执行 GitHub 或外部系统写操作；具体操作须由人、Agent 或下层自动化在各自授权范围内完成 |
| 分发范围 | 作为本仓库的知识资产发布；当前不由跨项目 `install` 安装 |
| 非目标 | 不替代项目事实、专业审批或平台自动化，不把 GitHub 的限制提升为通用研发原则 |

第一层回答“应该怎样研发”。`docs/workflows` 与 `skills` 按八个生命周期阶段路由，`templates/delivery` 保存跨阶段记录契约，`docs/exercises` 验证流程是否真正可执行。内容治理只负责这些知识资产的所有者、状态和复审期限，不负责目标 GitHub 仓库的设置。

## 第二层：GitHub 生命周期自动化

| 项目 | 定义 |
| --- | --- |
| 目标 | 把第一层中稳定、重复且可机械验证的规则落实为 GitHub 原生编排 |
| 受众 | 使用 GitHub PR、Actions、Release 和 Issues 的独立开发者或微型团队 |
| 输入 | 生命周期 policy、PR/Issue/Release 状态、结构化声明和非敏感证据链接 |
| 输出 | PR 门禁、Draft Release 候选、普通事故状态记录、复盘与只读审计结果 |
| 写权限 | 只读检查默认无写权限；Release、事故和复盘写操作仅由维护者显式触发并使用 job 级最小权限 |
| 分发范围 | 作为 manifest 的 `github-lifecycle` 组件进入自动化包并安装到目标仓库 |
| 非目标 | 不验证证据真实性，不批准高风险变更，不执行正式发布、部署、回滚或安全取证 |

第二层回答“哪些研发规则可以由 GitHub 确定性执行”。它可以引用第一层的风险和证据概念，但不得反向改写通用流程。生命周期运行逻辑不得执行跨项目安装或仓库引导；确定性打包仅作为第三层使用的边界能力。

## 第三层：跨项目安装与治理工具

| 项目 | 定义 |
| --- | --- |
| 目标 | 将第二层安全复制到其他仓库，诊断本地与远端漂移，并显式配置 GitHub 仓库 |
| 受众 | 自动化维护者和目标仓库管理员 |
| 输入 | 固定 tag 或完整 commit SHA、版本化 manifest、目标仓库路径与 GitHub 状态 |
| 输出 | 确定性自动化包、安装计划、诊断报告和仓库引导计划 |
| 写权限 | `package` 只创建本地归档；`install` 只写目标仓库本地文件；`doctor` 只读；`bootstrap` 仅在 dry-run 关闭且确认字符串精确匹配时写 GitHub 设置 |
| 分发范围 | 作为 manifest 的 `cross-project-governance` 组件随自动化包发布 |
| 非目标 | 不制定生命周期规则，不安装第一层知识资产，不覆盖冲突文件，不绕过权限、ruleset 或真实 check 证据 |

第三层回答“如何把第二层带到其他项目并持续确认其状态”。当前只治理 `github-lifecycle`；未来新增资产类型必须升级 manifest 或工具契约，并单独定义安装、冲突和诊断语义。

## 依赖方向与内部支持面

```text
研发知识与 SKILL
        ↓ 被选择性落实
GitHub 生命周期自动化
        ↓ 被打包、安装和治理
跨项目安装与治理工具
```

- 第一层不依赖运行时代码或 GitHub 仓库状态。
- 第二层遵循第一层的概念与安全边界，不调用 `install`、`doctor` 或 `bootstrap`。
- 第三层读取第二层的 policy、manifest 和 GitHub 状态，不复制一套独立的风险、事故或复盘规则。
- 跨层文档或公共 CLI 可以作为组合入口，但不能改变各层的授权和失败语义。

`.github/workflows/repository-checks.yml`、`.github/dependabot.yml`、`bin/playbook`、`scripts/development.py`、开发依赖和测试属于内部支持面。它们维护并验证三层资产，但不是第四个对外产品层，也不得进入自动化 manifest。

## 版本与变更规则

- 三层随同一个仓库 tag 发布；知识、自动化和治理工具不建立独立 release train。
- manifest schema 是跨项目包的机器兼容契约。schema 1 作为 legacy bundle 继续可读；本仓库从 schema 2 开始用 `github-lifecycle` 和 `cross-project-governance` 两个互斥组件生成包。
- 改变责任、写权限、分发集合或允许依赖时，必须同时更新本文、相关导航、manifest、仓库自检和测试。
- 自动化包不得包含第一层目录或内部支持面；组件文件必须存在、路径安全、排序稳定且不能跨组件重复。
