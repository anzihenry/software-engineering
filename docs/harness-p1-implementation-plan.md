# Harness P1 规范落实计划

## 目标、依据与状态

P0 已通过 [PR #40](https://github.com/anzihenry/software-engineering/pull/40) 合入 main；本计划固定调研基线 `c8b47b6f53813a91308e171905a62750ba08d1fd`，继承[落实矩阵](harness-requirements.md)、[质量门禁](quality-gates.md)、[证据与信任](evidence-trust.md)、[采用与复验](harness-adoption.md)。P0 计划明确留给 P1 的范围是领域专项扩展、运行指标体系和渠道部署适配。

P1 的目标是让后端与 Web 项目能够按风险选择专项、执行真实场景、判断证据并持续复验，再把同一候选交给实际交付渠道。用户已选择后端与 Web 优先；移动端、全平台覆盖和生产推广不在首批范围。本文件是待实施计划，不新增生效规范，不宣称项目已接入、指标已改善或渠道已部署。

当前已有后端五类、Web 三类专项 SKILL、系统验证、效果度量、内容复审、候选/渐进发布/恢复/收口指导，以及语言 adapter、安装/升级与 canary。P1 复用这些能力，补充项目配置、场景/报告契约、执行示例和重复验收；不把现有指导说成没有实现，也不因 P0 已通过而认为所有领域已自动强制。

## 首批范围与责任边界

- 第一层：细化既有 SKILL 的触发、输入、场景、报告、失败回流和示例；需要项目正式输出的模板提供中英版本，相关职责变动同步 workflow、skills 路由与要求映射。没有独立且重复的新职责时不新建 SKILL。
- 第二层：复用稳定 validate 与 lifecycle-policy、既有追溯和候选记录，接收项目执行结果；不让机械汇总替代内容真实性、专业审查或生产授权。
- 第三层：复用 custom/external adapter、安装/升级/doctor/bootstrap；不把第一层或本仓库内部测试、指标脚本自动纳入安装包。
- 实际部署流程由目标项目已有交付机制承担，P1 提供项目侧参考、配置和验收；不默认增加第二层正式发布/部署/回滚写权限。确需改变[三层边界](project-boundaries.md)、分发或机器契约时，先独立提出兼容与迁移方案，不能藏在 adapter 中实现。
- 既有强制要求缺口仍按原门禁修复，不借 P1 排期、指标不足或“稍后试点”豁免文档、翻译、独立性、必过 CI 和高风险人类决定。

规模是可独立审查/验证/回退的变更切片估计，不是人日或发布日期。每包先解决关键未知项，按“契约/示例 → 实现 → 正反例 → 独立验证 → 提交”推进；每个工作包完成并提交相关修改后再进入下一包，延续用户要求的逐步提交方式。

关键路径为 P1-01 → P1-02 → P1-03 → P1-04。前期可以盘点指标来源、项目和渠道，但不提前写远端设置或部署。实际团队容量、目标项目、外部审批和工具可用性确认后重估，不承诺固定日历时间。

## 开始 P1-01 前的准入盘点

在本计划基线上核对首批后端、Web 及其跨边界旅程，形成文件级清单：要求 ID/完整原文、触发条件、支持矩阵、实际项目事实、执行者/决策人、工具/人工验证、失败动作、证据与完成条件。角色映射到目标项目实际负责人；本计划角色不冒充已分配的人。

代表性来源包括后端[契约与集成](../skills/05-integration-validation/backend-contract-integration-validation/SKILL.md)、[安全授权](../skills/05-integration-validation/backend-security-authorization-validation/SKILL.md)，Web [功能兼容](../skills/05-integration-validation/web-functional-compatibility-validation/SKILL.md)、[视觉可访问性](../skills/05-integration-validation/web-visual-accessibility-validation/SKILL.md)及[系统验证](../skills/05-integration-validation/system-level-validation/SKILL.md)。固定基线中的 REQ-82f2677516fe448c（替身差异）、REQ-2671bc2136fe8b45（真实授权入口）、REQ-f3ef88e00fa56314（真实集成）、REQ-f61544ae9054a59c（批准视觉基线）、REQ-69fa1d975f3d76a8（键盘路径）可作为首批验收锚点；它们是选样，不是完整要求清单，不能忽略其他已触发强制项。

保留 P0 的 ID、退役和历史可达性；新增/修订来源同步维护清单，不能把提案中的未来要求直接当作已生效要求或已验证采用状态。先核既有工具/配置，再决定需要新增的执行载体；不升级工具链或生产依赖以迎合示例。

## P1-01：后端与 Web 专项执行契约

### 动作与资产

1. 建立可复用的“要求/风险 → 适用专项 → 场景/环境/阈值 → 实际执行 → 原始证据 → 单项结果 → P0 节点判定”契约；复用[验证矩阵](../templates/delivery/verification-matrix.md)和既有追溯字段。若需要机器报告 schema，先明确版本、旧报告处理、兼容边界与消费者，不静默修改既有 schema。
2. 后端先细化真实 HTTP/事件契约、错误/超时、默认拒绝和对象级授权，再按变更触点接入数据一致性、并发/性能、韧性恢复。Web 先细化浏览器真实路径、加载/空/错误/过期/恢复，再纳入视觉基线、键盘/辅助技术和性能；不以功能测试替代其余已触发专项。
3. 支持矩阵与通过阈值由项目事实和责任人确认，包括 API/消费者版本、数据量、浏览器引擎/视口、辅助技术、性能预算与环境差异。环境不足记 blocked/not-run，不从其他成功报告推导通过；不适用须有触发条件分析和独立核对。
4. 在隔离参考项目执行至少一条真实浏览器 → 后端完整路径及失败恢复，保存请求/响应、浏览器日志、场景输出和版本；实际跑项目工具，不用模拟 argv 代替运行。必要依赖替身明确区别于真实边界。
5. 优先扩充 backend-validation、web-frontend-validation、专项 SKILL 与 system-level-validation 的 references/示例；更改职责时同步阶段 3–5 路由、skills 导航、模板及要求映射。不可机械判断部分保留非作者评审。

### 验收

正常全链路与单项汇总一致；至少验证未经授权访问、协议不兼容、关键浏览器/键盘路径缺失、未批准视觉基线、性能阈值失败、环境或原始报告缺失、旧候选、只提供替身证据被正确识别。阈值不通过不能更新基线消除失败，未触发专项明确写理由。全部适用必过项有当前证据，单项“有条件通过”不能越过 P0 的合入/候选/生产边界。

## P1-02：运行指标与持续复验

### 动作与资产

1. 区分 harness 使用/执行质量与目标产品业务/SLO；按[效果度量](../skills/08-measurement-and-retrospective/outcome-measurement/SKILL.md)记录定义、分子分母、单位、来源、时间窗口、去重、缺失/取消/失败分类与适用限制。先收基线，不在无数据时承诺提升比例。
2. 首批仅采集决定可行动改进的指标：已触发且适用要求的有效证据覆盖；被独立复核的阻塞样本中误阻塞占比；按原因分类的阻塞；检查耗时/重跑次数；需复验对象的逾期与关闭情况。明确每个指标的实际 owner 和采集对象，不将评审样本比例冒充总体误阻塞率。
3. 优先从已有 CI、采用/评审/门禁记录只读提取最小字段，保存可追溯原始位置，形成指标字典和可复现汇总。无事件时显示无数据，分母未知或为零不写 100% 成功；重复/重跑、时区、观察窗口及变更前后口径不一致须可发现。
4. 定义复验触发：入口/知识 pin/要求、命令/工具/依赖、环境/支持矩阵、责任、权限/规则改变或内容复审到期。复用采用诊断、内容治理及 playbook-evolution/improvement-action-tracking，输出对象、原因、owner、期限、解阻与效果判据；不自动改日期、豁免门禁或声称未执行的周期任务已启用。
5. 至少对两个不同候选/采集时点真实重跑并复算，说明样本量和短窗口限制；保护密钥、个人/生产数据与敏感风险证据，不以这些指标进行个人绩效排名。

### 验收

口径可独立复算；缺数据、零分母、重复事件、时间/版本混用、只复核部分样本和采集失败均不会伪造改善或通过。注入知识/入口/环境/权限变化与复审到期，确认触发对应复验；完成复验后当前证据恢复，旧报告仍保留。缺关键采集时记录限制或阻塞，不能降低既有门禁。

## P1-03：项目侧交付渠道适配

### 前置探索与动作

1. 由项目负责人选定后端与 Web 各自的实际交付目标、环境和机制，先评估能复用的现有 CI/CD。用户已确认采用隔离合成本地后端/Web 渠道；本轮不使用云账户/区域。具体进程身份、对象、健康信号与恢复条件仍须进入本包前落到配置；探索退出条件是形成可审查的最小方案与明确授权范围，或明确不可实施原因。
2. 按[CI/CD 模式](../skills/05-integration-validation/github-actions-bootstrap/references/cd-modes.md)先验证 ci/artifact：真实构建同一候选，记录 source SHA、配置/依赖、制品摘要、保留期和原始构建报告，再由渠道消费同一不可变制品；不在部署步骤重建另一份。
3. 只有实际目标、短期身份/最小权限、环境保护、部署命令、健康窗口、失败/超时、停止和恢复均可验证时才进入 deployment。参考流程放项目侧或第一层 references/模板，不扩张第二层写入范围；密钥只记录名称与受控位置。
4. 先在明确隔离的测试目标或已授权 staging 执行；记录目标身份、原始平台/进程输出、部署标识、制品摘要和健康结果。演练失败、取消、重复/并发执行、暂停与恢复，不把提交成功或健康接口单点成功当整体发布成功。
5. 复用 release-candidate-preparation/release-readiness、progressive-release-execution、release-health-assessment、release-recovery-execution、release-closure 的现有权限/观察规则；生产仍需单独具体人类 Go/No-Go，不由 P1 计划或演练自动获得授权。

### 验收

后端、Web 的选定渠道各有一次真实候选交付和一次失败/恢复演练；全过程同一摘要，变更候选、凭据不可用、目标不匹配、健康失败和缺授权均阻塞或停止扩大。明确区分本地模拟、真实隔离/staging 与生产；只完成 artifact 时仅关闭其子切片，不关闭 deployment 或整个工作包。具体平台未确认时不承诺本包完成。

## P1-04：跨项目闭环与兼容验收

### 动作与验收矩阵

1. 为首批领域选择新项目与有现存入口/CI/文档的成熟项目，保留项目已有命令、规则和本地修改；涵盖至少一个后端项目、一个 Web 项目和一条两者真实系统路径。用例维度包含领域、风险、项目成熟度、CI/交付模式与证据来源，不把每个维度的全笛卡尔积设为无依据成本。
2. 复用固定版本、采用清单、Git 任务分支、安装/升级/doctor 和[现有离线矩阵](cross-project-acceptance.md)。现有 16 组合只证明安装/治理契约；本包补真实领域工具、浏览器/协议、渠道和非作者任务的证据，不改写旧验收为全平台覆盖。
3. 执行正常闭环、缺必需专项/译文/来源、旧报告、候选/制品/环境漂移、规则漂移、采集失败与渠道健康失败；验证每项在正确节点阻塞、修正后复验，并检查上游到结果的唯一记录链。
4. 在固定旧/新版本上验证升级、同版本重跑与回退预案；保护成熟项目的本地修改、未知文件、冲突和上游删除项。若新增资产类型或机器契约，先更新边界/兼容/manifest/检查及受影响的矩阵，再测试；不把第一层或内部支持面悄然加入安装包。
5. 实际 GitHub 试点需要当前 PR 的真实 check/App、受控来源与规则回读。P0 canary 可作为候选，但新的 PR/设置/外部渠道操作按实际 scope 和既有授权核对；不能把上一轮仅追加一个 status 的授权扩为任意远端写入。
6. 多人写入、组织/第三方 App、token 分发或复杂权限项目先审计完整实际写入路径；无法审计则阻塞该模式，必要时提出受控 App/服务接入方案。P0 单 owner 的 API 可见验证不构成全量权限安全证据，也不替代新候选真实评审。

最终输出分领域/项目/环境的通过或阻塞结论、实际读取/执行/平台原报告、版本/制品/部署身份、问题与复核、迁移与操作指南。离线/非 GitHub 场景可据事实标对应平台不适用；GitHub 项目缺权限/工具不得靠改 scope 伪造完成。测试/模拟不能替代申明的真实渠道或生产能力。

## 总体验收与完成边界

四包均完成后才能报告首批 P1 已实施：适用强制要求覆盖与实际执行、后端/Web真实专项和系统路径、可复算指标及漂移复验、两领域选定渠道的交付/失败恢复、成熟项目升级/本地修改保护、当前版本非作者验收均有证据。未完成的真实渠道、权限审计或必过项保持相应包阻塞，不由“已有模板/工具/样例”替代。

每步保留完整 source/head/base/merge、适用的制品/部署、环境/工具和报告，相关变更重验；风险由实际负责人决定，不能用观察指标自动批准条件结论。实施完成、某项目采用、具体生产发布分别判断，不声称全浏览器、全平台或其他项目已经生效。

## 最初计划交付与后续文档影响
