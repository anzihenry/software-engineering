# 项目文档规范

[English](documentation-standard.en.md)

## 适用范围与资产边界

本文是软件研发 harness 的通用文档规范，覆盖目标项目的研究、产品、设计、工程、计划、使用、运营和发布。规范版本为 `0.1.0`；“必须”表示项目采用该规范后的强制要求，“建议”表示可裁剪的实践。

`software-engineering` 是规范、workflow、SKILL 和模板的资产仓库，保留既有结构。下面的目录属于使用 harness 研发的目标项目，不要求资产仓库按目标项目目录重排。规范及模板属于第一层知识资产，不进入现有 GitHub 自动化安装包。

规范和模板已接入 harness 入口、八阶段 workflow 与文档维护/独立验证 SKILL，作为使用本 harness 研发的默认要求。目标项目检查器与 CI 模板已提供，实际门禁按[工具接入](documentation-tooling.md)配置和验证后生效。使用方式见[文档治理接入](documentation-integration.md)。

## 组织原则

- 长期文档按知识领域维护当前事实；具体工作的过程按专题组织；历史记录保存当时的背景和证据。
- 一个正式定义、任务状态或原始材料必须只有一个维护位置，其他位置通过链接引用。
- 目录按需创建；小专题可合写，复杂专题可拆分。裁剪文件数量不能削弱双语同步、验收或独立评审要求。
- 历史内容不必描述当前实现，但必须明确状态、时间和适用版本，防止被当作当前依据。

## 目标项目目录

```text
README.md / README.en.md
CHANGELOG.md / CHANGELOG.en.md
docs/
├── README.md / README.en.md
├── documentation.md / documentation.en.md
├── research/
├── product/
├── design/
├── engineering/
│   └── decisions/
├── guides/
├── planning/
├── initiatives/
│   ├── feature/
│   ├── improvement/
│   ├── refactor/
│   ├── research/
│   └── process/
└── releases/
```

| 位置 | 职责与边界 |
| --- | --- |
| 根 README | 项目用途、核心能力、最短可用示例、环境要求、文档入口、许可证；详细操作链接 guides |
| 根 CHANGELOG | 按版本记录变更摘要；详细兼容性、验收和正式发布状态链接 releases |
| docs/README | 文档地图、按读者需求编写的阅读路径、领域入口 |
| docs/documentation | 本项目采用的规范版本、维护责任、检查命令、评审机制和迁移配置 |
| research | 面向产品、可供多个专题复用的研究结论；注明来源、研究时间、适用范围与局限 |
| product | 当前生效的产品方向、能力、业务规则、目标用户和成功指标；具体变更需求放专题 |
| design | 当前用户旅程、信息架构、交互与视觉规则、设计系统；技术方案放 engineering |
| engineering | 当前架构、模块边界、数据模型、接口契约、安全与性能约束、长期技术决策 |
| guides | 可重复执行的使用、开发、测试、部署、运维、恢复和发布操作说明 |
| planning | 跨专题路线图、优先级、里程碑、资源、依赖、整体风险和协作规则 |
| initiatives | 一项工作的需求、研究、方案、计划、验收与复盘过程 |
| releases | 版本或明确发布事件的交付内容、兼容性、验收证据、产物与实际发布状态 |

为专题开展的研究资料跟随专题；独立研究可建立 research 类专题。原始材料保留一份，长期复用的结论提炼到 research 并链接来源。项目任务若在 Issue 等系统维护，计划文档记录目标、里程碑和任务链接，不能复制一套任务状态。

## 专题分类与内部文件

分类按主要目标选择，一个专题只属于一个分类：`feature` 新增能力、`improvement` 改善已有能力、`refactor` 内部结构重构、`research` 专项研究、`process` 流程改进。

建议围绕有明确目标、能独立判断完成、需要持续维护多类信息的工作建专题，例如 `initiatives/feature/adapter-upgrade/`。专题可以跨版本、含多个阶段。小型修复可用 Issue/PR 记录并更新长期文档，无须建专题。

每个专题必须有 README 和英文版，写明目标、范围、状态、负责人、完成条件和导航。按需增加 `requirements.md`、`research.md`、`design.md`、`plan.md`、`validation.md`；复杂设计可拆成 experience-design 和 technical-design。所有拆分的正式文档必须双语。完成结论和交付检查可放 validation，也可合写在 README。

## 状态与生命周期

| 对象 | 状态 |
| --- | --- |
| 长期文档及索引 | draft 草案；current 当前有效；superseded 被替代或不再适用 |
| 专题入口 | proposed 提议；active 推进中；paused 暂停；completed 达到完成条件；cancelled 终止 |
| 发布入口 | planned 计划；verified 指定候选已验收；released 正式发布；cancelled 终止；withdrawn 撤回 |

专题内的需求、方案和报告描述专题当时的记录，使用长期文档状态；`current` 表示该记录在所注明的专题与版本范围内有效，不能替代项目当前知识。专题入口独立表达推进状态。

暂停必须记录原因和恢复条件；终止必须记录原因及已有成果处理方式。专题 completed 前，必须完成验收、更新受影响的长期文档及英文版、关联证据和文档、将遗留事项转入明确的任务或后续专题。completed 不等于正式发布。

归档通过状态和索引展示，保留原路径。superseded 必须说明原因及替代关系；没有替代文档时说明为何不再适用。历史事实错误可补充更正，后续行为变化由新记录和长期文档体现。

verified 必须绑定候选摘要和源码提交；候选变更需重新验收。released 必须记录发布时间、产物身份、发布地址与发布证据。cancelled/withdrawn 必须说明原因；withdrawn 还需提供后续使用建议。

## 命名、元信息与双语

目录和文件必须使用英文小写 kebab-case；保留名称 `README.md`、`CHANGELOG.md` 及其语言变体（如 `README.en.md`、`CHANGELOG.en.md`）除外。入口固定 `README.md`。稳定主题命名，不在专题路径嵌入状态、负责人或阶段。发布目录按版本或稳定发布事件命名；重复记录可加 `YYYY-MM-DD` 日期。技术决策用四位编号，例如 `engineering/decisions/0001-preparation-boundary.md`，编号不复用。

正式维护的文档必须以 YAML 元信息开头：

```yaml
title: 文档标题
status: current
owner: technical-lead
updated: "2026-10-09"
```

`owner` 为人员或稳定角色，项目配置必须能将角色映射到实际维护者。`updated` 是最后实质更新或有效性复核日期，格式调整不必更改。版本、来源、适用范围、替代关系可增补字段，不能伪造日期、责任或证据。

中文为主语言，标准文件名不加语言后缀；英文使用 `.en.md`。其他语言按需增加。正式长期文档、专题入口与拆分文件、发布记录均必须提供英文。两种版本互链，同一对象的 owner/status 一致；updated 各自记录实际更新或复核日期，不要求日期相同。

英文未同步时明确标注其落后范围和对应中文版本，不得通过本次交付检查。原始访谈、日志、生成报告等可保留原始语言和格式，由双语入口或摘要说明用途、来源与适用范围。

## 模板与既有追溯契约

模板统一必要内容，允许调整章节和拆分；必需项不适用时写明原因。模板资产的元信息描述模板本身；复制到项目时必须替换文档元信息和全部占位内容，选择所属对象的合法状态，重新检查链接。草案和模板不构成已验收证据。

| 类型 | 必要内容 |
| --- | --- |
| 长期文档 | 当前事实或规则、适用范围、引用 |
| 专题入口 | 目标、范围、状态、负责人、完成条件、导航 |
| 需求 | 用户问题、预期结果、范围与非目标、验收标准 |
| 研究 | 问题、方法与样本、发现、局限、来源 |
| 方案 | 背景与约束、方案、关键决策、风险、验证方式 |
| 计划 | 任务、依赖、负责人、进度、风险、完成条件 |
| 验证 | 验收、证据、遗留问题、文档检查、独立评审 |
| 发布 | 版本与状态、内容、兼容性、产物、验收和发布证据 |
| 技术决策 | 背景、备选、决策与理由、后果、替代关系 |

本仓库既有 workflow/SKILL 的 `active/deprecated`、`scope/review_by` 继续由内容治理管理，SKILL 保持标准 frontmatter。它们不是目标项目文档状态，不能批量替换。普通文档过复核期限标记待复核，不自动改变 status；workflow/SKILL 的现有过期门禁仍生效。

既有 delivery 模板的稳定 record_id、related_records、source_version、evidence 和带时区 created_at/updated_at 保留。文档的 updated 表示内容复核日期，记录的 updated_at 表示事件或状态更新时间；两者用途不同。记录状态与文档状态分开，例如在正文追溯区记录 record_status，不能让一个 status 同时代表专题、需求和发布。

## 导航、引用与证据

创建领域目录时必须提供双语 README；子目录在确需独立导航时增加入口。initiatives 索引按分类和状态列专题；releases 按版本与发布状态列记录。标题与状态以文档元信息为准，阅读路径和用途人工编写；生成索引不能成为第二份事实来源。

仓库内必须使用相对链接，同语言优先，必要时链接章节。英文引用未翻译的原始材料时注明语言。详细定义、任务状态、原始材料和共享证据只维护一份。目录或状态改变时更新导航与受影响链接。

长期技术决策集中放 engineering/decisions，专题方案链接决策；实施后更新当前架构与契约。改变长期决策时新增编号记录，旧记录标记 superseded 并链接新记录。

`assets/` 就近存放图片和设计附件，`evidence/` 存放报告和测量数据。专题证据跟随专题，版本级证据跟随发布；可共享引用。必须注明生成方式、时间、源码提交或产物摘要、适用环境。大型或敏感材料使用受控外部系统，保存地址、标识和必要身份信息，不复制密钥或未脱敏个人数据。

## 严格交付检查

合入、专题 completed、版本 released 是强制检查节点。交付负责人使用统一检查模板，普通变更记录在 PR，专题记录在 validation 或合写入口，发布记录链接检查结果，避免复制结论。

必须显式列出产品、研究、设计、工程、指南、计划、专题、发布与导航的影响；每项为“已更新”“经检查无需更新”或“不适用”，后两者必须说明理由。工具检查必填元信息、合法状态、命名、链接、双语配对与索引一致性；人类或独立 AI Agent 核对影响完整性、实际行为、双语语义、证据与适用示例。英文文件存在不能证明翻译正确。

独立评审者不能是本次内容的作者或修改者；独立 Agent 必须另起评审上下文，独立读取实现、文档与证据，不能只复述作者摘要。记录身份、所评审提交或未提交文件摘要快照、实际读取文件、问题、修正复核和最终结论。发现问题由作者修改，评审者复核。检查通过后相关修改使受影响结论失效，必须重新检查。

全部必过检查通过、独立评审通过、双语同步、无本次必需文档问题时才能交付。必需更新、翻译或证据缺失不能豁免；无关既有问题可单独跟踪，但必须说明不影响本次交付的依据。人类高风险 Go/No-Go 等既有授权要求仍适用，文档评审不替代专业审批。

定期复核补充交付检查，owner 核对实际有效性后更新 updated；不能只批量改日期。自动检查不能判断内容真实性或代替独立评审。后续实现须将机械检查和评审记录一致性接入必过门禁。没有专用检查器时，必须逐项实施有证据的人工或临时工具检查及独立评审；明确执行方式，不能把未实现、未执行的自动检查记为通过。项目已经要求的 CI 检查仍必须真实通过。

## 项目采用与迁移

目标项目 docs/documentation 必须记录固定规范版本或提交、责任映射、任务事实来源、实际检查命令与 CI 门槛、独立评审记录位置、复核周期和外部资料位置。公共规范由 harness 维护，项目填写执行配置，不复制一份无来源的规则。

已有项目先建立清单、归属、状态和负责人，优先修复当前文档错误，再分批补齐目录、元信息、双语和导航。迁移清单必须有责任人、完成条件与证据；新变更立即遵守规范，受影响旧文档随交付补齐，不能借迁移未结束绕过门槛。迁移完成须独立验收。不会因采用规范而自动移动目录或覆写项目资产。
