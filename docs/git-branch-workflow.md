# Git 分支开发与管理规范

## 适用与采用

使用本 harness 的 Git 项目默认遵循本文，代码、文档和配置修改同样适用。默认分支及其他受保护分支统称基线分支；新项目默认 `main`，已有项目使用实际默认分支。非 Git 项目标记不适用。用户明确要求或项目更具体的规范优先；偏离必须说明依据，不由 Agent 静默决定。

本文维护分支操作的唯一规则来源；[Git 任务分支管理技能](../skills/04-implementation-and-self-test/git-branch-management/SKILL.md)负责按实际操作执行。[仓库治理基线](github-repository-defaults.md)负责 GitHub 远端保护和自动删分支设置；本地操作规则不自动获得远端写入或 PR 合并权限。采用时将[项目入口模板](../templates/codex/AGENTS.md)的分支条款合并到既有入口，保证本文中文固定版本可访问，或提供项目提交的等价规范。第一层资产不由现有 GitHub 自动化安装器复制；仅安装自动化包不证明 Agent 已加载本文，也不代表平台已强制本地分支规则。

## 1. 修改前检查与任务分支

修改任何文件前先读取项目入口和更具体的分支规范，再检查当前分支、工作区、远端及实际默认分支，执行 `git fetch` 获取远端状态；检查是否已有对应任务分支，包含其他 worktree 中的分支。记录任务分支、基线和同步结果。读取和检查可在基线分支进行。

- 当前在基线分支时，先创建或切换到功能分支，再开始修改。工作区干净时，新分支从最新远端默认分支创建。
- 已在对应任务的功能分支上时复用，不重复创建。当前分支属于另一任务时，不把新任务混入该分支。
- 有其他任务的未提交修改时，保留并先确认归属；不自动丢弃、暂存、提交或搬移。属于本次任务但已经误改基线分支的内容，按第 5 节恢复。
- fetch 失败、默认分支未知或没有可用远端基线时，报告具体缺口，不声称已同步；需明确初始化或离线基线后再创建新分支。

## 2. 默认分支的本地使用边界

本地默认分支及其他受保护分支用于同步远端、查看和运行验证，不承载任务修改或新提交。会修改文件的格式化、生成等操作同样先进入任务分支。任务提交只在功能分支创建，通过 PR 合入默认分支。

用户说“提交”或“推送”时，默认操作当前任务功能分支，不解释为直接提交或推送 `main`。提交前核对暂存范围，推送前核对 remote、分支及 upstream；不把无关工作或其他分支一并提交/推送。

## 3. 命名、任务边界与复用

Agent 创建的功能分支使用 `<当前 coding agent 标识>/<简短任务名>`，例如 `codex/github-governance-defaults`、`deepseek-harness/github-governance-defaults`。任务名使用英文小写和连字符；标识从当前 Agent/运行环境确认，不猜测身份。

一个分支对应一个可独立评审的任务。已有对应任务分支则复用；同一任务更换 Agent 后不因此重命名。用户明确指定名称或项目已有更具体规范时，遵循该规范。名称已被其他任务占用时不覆盖分支，选取能区分任务的名称。

## 4. 同步远端与分支落后

开始任务前 fetch；复用任务分支时核对与远端任务分支、默认分支的差异，保护未提交修改和未推送提交。修改历史或整合前先保证工作已安全保留，不以 `reset --hard`、`clean` 或自动 stash 代替归属确认。

- 未发布、仅自己使用的功能分支可通过 rebase 同步最新远端默认分支。
- 已推送且多人或多个 Agent 共用的分支默认通过 merge 同步，避免改写他人依赖的历史；项目另有规范时遵循项目规范。
- 已推送但是否共用不明确时先确认；不因一个分支带有自己的 Agent 前缀就认定可改写。不得直接强推覆盖远端。
- 冲突在任务分支解决；语义无法确定时先确认，不使用一侧全量覆盖掩盖冲突。同步后重新运行受影响检查、记录最新提交并刷新受影响评审证据。

## 5. 误在基线分支修改或提交时恢复

1. 停止继续提交或推送基线分支，检查未提交内容、本地新增提交和远端状态。
2. 先将本次修改和提交安全保留到对应功能分支，核对文件、提交及工作区内容均没有遗漏；其他任务的工作先确认归属。
3. fetch 后确认本地基线分支没有其他待保留工作，也没有被其他 worktree 使用，再恢复为与远端一致。不得先重置再尝试找回修改；不能满足前提时保留现状并报告待处理项。
4. 在功能分支按第 4 节同步、解决冲突、重新验证，再推送并创建 PR；恢复说明记录原提交与新分支/提交的对应关系。
5. 已经推送到远端默认分支时，不通过强推撤销历史，按项目流程通过修复或回退 PR 处理。

## 6. PR 合入后的分支清理

先确认 PR 已合并，再验证远端功能分支是否已自动删除；设置开启不等于实际删除成功。自动删除失败时，确认 PR 的精确 head、分支未被复用且没有新增待保留提交，再按已有授权清理；授权不足时给出具体待清理对象。

本地功能分支仅在没有未提交修改、没有未合入或待保留提交、且未被其他 worktree 使用时删除。先安全切换到默认分支并同步远端，不能用强制重置清掉默认分支上的工作。不能满足前提时保留分支并记录原因。

Squash 合并可能改变提交身份，判断是否可清理时结合 PR 状态、精确 head、实际内容和合并后新增提交；不只依赖 Git 的“已合并”判断，也不把 Git 拒绝安全删除当成直接强制删除的理由。即使有清理授权，待保留工作也不得删除。不批量删除归属不明的历史分支。

## 阶段路由与交付证据

| 时机 | 执行入口 | 必需记录 |
| --- | --- | --- |
| 修改前及实现 | [Git 任务分支管理](../skills/04-implementation-and-self-test/git-branch-management/SKILL.md)，由[开发与自测](workflows/04-implementation-and-self-test.md)调用 | 当前分支/工作区、任务归属、实际基线和 fetch 结果 |
| 提交、推送与 PR 交接 | [交接准备](../skills/04-implementation-and-self-test/change-handoff-preparation/SKILL.md)、[PR 集成](../skills/05-integration-validation/github-pr-integration/SKILL.md) | 任务分支、base/head、同步/冲突处理和检查证据 |
| 合入判断 | [合入就绪](../skills/05-integration-validation/merge-readiness/SKILL.md) | 最新 SHA 的检查与评审，无阻塞冲突；不以分支命名代替内容核对 |
| 误提交恢复、合入后清理 | 本文第 5、6 节；首次引导另遵循[Bootstrap 收口](../skills/05-integration-validation/github-repository-bootstrap/references/bootstrap-finalization.md) | 原提交与恢复位置、PR/精确 head、远端删除结果、本地 worktree 与待保留工作核对 |

GitHub 操作用 `gh`，本地分支、fetch、提交、推送用 `git`；身份、权限和平台限制遵循项目既有规则。未验证或未执行项明确记录，不能把本地操作成功当成 PR 已合入或远端规则已生效。
