# 阶段 2：澄清与立项

## 目标

把已批准澄清的机会形成足以开展方案设计的需求包。完成本阶段仅批准方案设计投入，不表示技术可行、开发已承诺或日期已确定；阶段 03 完成可行方案、投入与计划后，再由有权角色确认开发承诺。

## 输入

- 已按[阶段 01 门禁](01-demand-and-opportunity.md#决策门禁)批准投入澄清的主记录：问题/来源、可定性结果、初步范围/非目标、约束/风险、用户指定方案及假设、未解问题/负责人/下一步和实际决定。缺少上游批准时可整理草案/补充问题，不能伪造已立项或绕过上游判断。
- 已有业务规则、用户旅程、系统/接口/政策背景、项目责任和文档配置。已有完整材料直接引用，不重复创建一套事实来源。

## 流程

1. **确认问题和切片**：用独立需求 ID 关联原机会；机会和需求可同一 Issue 承载，但状态/决定分别维护。切片表达完整用户或系统结果，明确角色、前置、触发、范围/非目标及原约束，不按前端/后端机械拆分，不替用户改指定方案。
2. **形成验收**：按下节质量要求记录行为及适用非功能判据、来源和负责人；区分事实、假设和未决定规则，不填“正常/友好”了事，也不把内部步骤当结果。
3. **分类未知和依赖**：按本 workflow 的推进规则逐项标明缺口性质、决定/验证人、目标/判断条件、节点与失败动作。没有回复不算同意，有对接人不算已承诺，未来计划能力不能写当前可用。
4. **风险与控制**：识别影响、最坏后果、可逆性、检测/恢复和依据。涉及身份/权限、资金、敏感数据、对外 API/契约、数据迁移、关键基础设施、重大安全暴露或严格监管等既有触发项，按高风险要求处理；原规则更严格时遵循，不仅限不可逆迁移，不以代码少、工期紧或尚无事故降级。控制措施标明拟议/已验证及证据，不把计划审计/回滚当有效保障。
5. **对齐并决定**：产品/业务、开发及必要安全/合规/架构/运维等有权角色确认范围、验收、风险与设计投入。风险建议与实际确认分开，必需控制/评审列责任人、完成节点、证据和失败停止动作；进入方案前必需评估须实际完成，后续设计/发布验证按节点承接，不能以“已排队”代替通过或让 Agent 自批例外。采用[既有质量门禁](../quality-gates.md)，不减必过要求。

## 验收质量

| 要求 | 判断方式 |
| --- | --- |
| 描述结果 | 用户/系统可观察行为及结果，不以实现步骤或“做完功能”代替 |
| 条件明确 | 按需要写角色、前置、输入与触发，区分角色/状态差异 |
| 能够判定 | 明确预期与判断依据/方法，避免孤立的“正常、流畅、友好” |
| 覆盖适用风险 | 主流程及实际涉及的边界、失败、权限、取消/恢复等，不机械要求无关场景 |
| 可追溯 | 每条验收关联稳定要求 ID、原问题/约束与来源，变更能定位影响 |

不强制统一句式或所有要求数值化：小任务可清晰条目，复杂角色/状态可用表格或 Given–When–Then。适用性能、可靠性、可访问性、保留/正确性、审计、兼容/本地化等非功能要求，注明触发事实、来源、阈值或确认的定性判据、验证方式与负责人；不适用需理由。没有明确要求不能默认无要求；影响验收的未知阈值/规则在本阶段澄清，不编指标或全部后移。

## 未知项与依赖推进

| 未知类型 | 去向与必需内容 |
| --- | --- |
| 需求判断阻塞 | 业务规则/范围/验收不清留阶段 02，列问题、负责人和解阻动作；不把互相冲突的理解交设计猜测 |
| 技术方案待验证 | 需求结果已明确，列负责人、验证目标、判断条件、方案探索边界/退出及失败处理，交阶段 03；不预填可行或成功 |
| 非阻塞细节 | 不影响核心行为/风险时，写允许调整范围、负责人和确认节点；越界重新分类，不能无限悬置 |
| 高风险影响未知 | 先补适用专业评估，不能包装为普通技术待定或以排队放行 |

依赖分“已识别”（知道需要谁提供什么）、“待确认”（已有对接但内容/接口/时序未确认）、“已确认”（对应负责人接受具体条件且有可追溯依据）。逐项保留提供/消费方、负责人、内容/条件/所需节点、状态依据、失败影响和解阻动作；确认条件改变后重验，不自动沿用旧承诺。

进入方案不要求所有实施依赖已交付；但会改变需求范围、验收含义或关键风险判断的依赖必须先澄清。其他依赖只有在负责人、探索边界、验证/退出条件明确并获相应授权时才可带入，保留真实待确认/未交付状态，不把受控探索当整体交付保障。

## 决策门禁

进入阶段 03 前，需求主记录必须满足七项，并固定批准范围的当前基线；Agent 可提出建议和记录已授权事实，不代替有权负责人确认。

| 最小标准 | 必需内容 |
| --- | --- |
| 范围明确 | 完整结果切片、对象、范围/非目标、原约束与上游关联 |
| 验收可判定 | 符合上述质量要求，关键业务含义无冲突 |
| 适用非功能要求已识别 | 有来源/触发、判断方式和负责人，影响验收的关键判据明确 |
| 风险及必需评审清楚 | 等级/触发/理由、控制和评审节点/责任/证据；本节点必需项实际完成，后续项不虚报通过 |
| 关键依赖有依据 | 事实/确认来源与影响清楚，阻塞范围/验收/关键风险的依赖已澄清；其他按受控探索规则交接 |
| 未知项有去向 | 分类、负责人、验证/确认目标、节点/退出及失败动作；无本阶段必解决缺口 |
| 有权批准进入方案 | 实际确认主体/权限依据、理由、时间及时区、基线版本及范围/限制；不等于开发/日期承诺 |

## 需求状态与基线变更

本节是需求状态和变更的规则来源。需求状态不与机会、文档 frontmatter、专题或发布状态共用；状态/负责人只维护一处，附件引用。

| 状态 | 含义 | 退出与记录 |
| --- | --- | --- |
| 细化中 | 正在明确业务规则、范围、验收 | 足以交相关负责人时进入对齐，发现明确阻塞则记录解阻 |
| 待对齐 | 有草案，正常等待相关方必要确认 | 分歧处理且确认可追溯后重新判断；发出请求不算确认，已知关键冲突不是正常等待 |
| 可进入方案 | 七项满足且实际批准设计投入 | 交接当前基线；不表示开发/日期批准，相关变更需重新判断 |
| 阻塞 | 已有关键缺口，当前不能推进 | 原因、负责人、解阻动作、复查条件；解决后重评，不直接恢复旧就绪 |
| 已取消 | 有权负责人决定停止本需求 | 原因/决定/证据、成果和下游处理；重启重新评估，不直接继承旧批准 |

转换保留原/新状态、原因、主体及权限、带时区时间和依据。没有实际决定时区分建议与事实，不给就绪或取消造批准；小团队可一人兼任，Agent 不因此自动获得权限。

需求确认时固定可引用版本/修订号或文件摘要、上游机会、范围/非目标、验收、风险/控制、依赖/未知及确认主体/时间。变更保留原基线、原因、确认、受影响标准/风险/依赖/下游、失效证据及可继续/需等待范围，不用旧批准覆盖新增内容，也不自动取消所有旧工作。

- 纯措辞且验收含义不变：原记录修订并保留理由，无需重走全流程。
- 业务规则/范围/验收改变：回阶段 02 评估和确认，受影响就绪结论失效；未受影响范围核对原授权后可继续，不能把全体标通过。
- 目标用户/价值/优先级改变：回阶段 01 重新判断，再决定后续方向。
- 纯技术方案改变：由阶段 03 处理，影响验收、成本约束或风险则反馈阶段 02。

旧记录保留 ID、旧状态/版本/来源/时间及无法取得材料；“可进入方案”旧标签不证明新七项达标，补当前证据、交有权角色重评，不追溯伪造批准。已取消记录重开保留旧决定，按当前条件重新确认。

## 文档治理

把本次需求、范围与验收标准放在专题或已有 Issue/PR 记录，生效的产品规则由 product 维护。列出初步文档影响、负责人和双语要求；小工作不强制建专题，新项目或迁移项目由文档维护技能补采用配置。

遵循[项目文档规范](../documentation-standard.md)和[接入说明](../documentation-integration.md)。[文档维护](../../skills/04-implementation-and-self-test/documentation-maintenance/SKILL.md)负责准备与更新，[独立文档验证](../../skills/05-integration-validation/documentation-delivery-validation/SKILL.md)负责检查结论，使用[统一交付检查模板](../../templates/documentation/delivery-check.md)。缺少专用检查器时保留逐项实际核对证据，不能声称第三阶段自动门禁已启用。

## 输出

- 一份需求主记录及当前基线：行为切片、验收/NFR、风险控制、依赖/未知、实际决定与状态历史；复杂内容链接附件，小工作可合写 Issue，不重复填三份技能表。
- 建议、已确认事实、拟议控制/未来能力与未决分别标注；使用同步中英需求模板及[本轮计划](../phase02-optimization-plan.md)，不把旧标签或模板存在当验证通过。
- 使用[需求与风险包模板](../../templates/delivery/requirements-risk-package.md)保留统一追溯字段和上游机会，不以合写删除独立 ID/状态。

## 异常与回流

- 业务规则或验收分歧留阶段 02；价值/优先级失效回阶段 01，不一律回上游。
- 范围过大拆完整结果切片，重评风险与依赖，不按技术层制造孤立交付。
- 高风险未知或不可接受影响先停止受影响推进，交相应有权角色判断；例外仅按[质量门禁](../quality-gates.md)原规则允许范围处理，不能豁免必需文档、译文、证据、独立性、必过 CI 或高风险/生产授权。

## 交接给下一阶段

交阶段 03：可引用需求基线及上游机会、行为/NFR验收、风险/必需控制及责任/节点/证据、依赖/未知的真实状态与验证退出条件、实际批准范围/理由/时间。已知指定方案与假设性质保留。阶段 03 按[完成与开发门禁](03-solution-and-planning.md#决策门禁)逐项回应，技术评审/实施准备/实际开发批准分开；需要编码的可行性验证作为worktree技术预研。业务含义缺失回阶段 02，价值失效回阶段 01，不能静默补需求或沿用失效批准。
