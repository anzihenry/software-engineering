# 阶段 2：澄清与立项

## 目标

将已确认的机会或问题收敛为各方理解一致、可验证、可估算的交付项。

## 输入

- 已排序的机会记录、调研证据、现状数据和业务约束。
- 相关系统、用户旅程、既有接口或政策信息。

## 流程

1. **界定边界**：拆分为可独立交付的用户故事、缺陷或技术任务；明确参与者、前置条件、主流程、异常流程和不在范围内的事项。
2. **定义验收标准**：以可观察的行为和结果写出完成条件；同时明确性能、可靠性、可访问性、数据保留等非功能要求。
3. **澄清依赖**：识别上下游团队、第三方、数据源、许可证和环境依赖，并确认责任人与时序。
4. **风险分级**：按低、中、高评估影响范围。涉及身份、权限、资金、敏感数据、对外契约、数据迁移或关键基础设施时，按高风险处理，触发相应专家参与。
5. **形成共识并立项**：产品/业务负责人、开发负责人及必要的安全、合规、运维代表确认验收含义、优先级和可投入性。

## 决策门禁

进入“方案与计划”前，验收标准必须可测试，范围和非目标明确，依赖有所有者，高风险项已进入设计/安全评审队列。存在关键未决问题时，不承诺交付日期。

## 输出

- 可实施的需求包：背景、范围、用户故事或问题描述、验收标准、非功能要求、依赖和风险等级。
- 立项决定及待决事项清单。

## 异常与回流

- 验收标准无法达成一致：回到需求与机会阶段，重新确认问题或优先级。
- 发现范围过大：拆分为独立可发布的最小交付项。
- 高风险影响无法接受：关闭、重新设计或申请明确的风险例外。

## 交接给下一阶段

交接完整需求包、风险分类及待决事项。方案阶段需逐项回应验收标准和高风险约束。
