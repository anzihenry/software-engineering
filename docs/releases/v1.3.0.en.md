# Software Engineering Harness v1.3.0

[中文](v1.3.0.md)

These are version notes. The [GitHub Release](https://github.com/anzihenry/software-engineering/releases/tag/v1.3.0) and its evidence attachments provide actual publication state/time, exact source SHA, and artifact digests. Scope is repository knowledge assets and the existing GitHub automation bundle; no production deployment or automatic target-project upgrade.

## Changes

- Phase01 approves clarification,02 approves solution work,03 separates evidence-backed design, executable planning, and actual development approval. Coding research runs in a worktree and retains evidence before cleanup.
- Phase04 covers complete implementation/self-testing/handoff;05 requires independent validation and end-to-end verification before and after each feature merge. Merging alone does not finish integration.
- Phase06 fixes candidate identity and valid authorization, batches and time/sample observation, reconciliation after interruption, recovery, and operations acceptance.
- Phase07 accepts operations/health/maintenance/incidents/support/restricted work by work unit; mitigation, recovery, and closure remain separate.
- Phase08 separates metric definitions/results/attribution/decisions, blameless reviews, implementation/effectiveness verification, and playbook trials/feedback.
- Eight phase directories contain 71 skills, 10 bilingual delivery-template pairs, three lifecycle exercises, and 152 independent cases; see the [lifecycle](../software-development-lifecycle.md) and phase validation reports (Chinese sources).
- Documentation maintenance/independent validation, bilingual target templates and check/snapshot/gate tools, risk/authority/source traceability, Git branch rules, and a Swift 6.4 minimum coding baseline. Respect committed project tooling; no silent upgrades.

## Distribution and Compatibility

Get complete knowledge assets from the [tagged source](https://github.com/anzihenry/software-engineering/tree/v1.3.0) or GitHub source archives. The `github-lifecycle.zip` and `.sha256` assets contain only manifest-defined layer2/3 automation, excluding skills, phase workflows, the full template collection, and internal validation tools. Candidate JSON, checklist, and release evidence are provenance rather than the installation bundle.

Manifest schema 3, four profiles, built-in adapters, legacy reading, and three-way upgrade contracts remain. This does not guarantee every older project/platform is compatible. Follow [UPGRADING](../../UPGRADING.md) and the [compatibility matrix](../version-compatibility.md) (Chinese) to verify old/new packages and installation records. Local modifications/conflicts block overwrites; no implicit deletion or profile/adapter switch.

Check the existing Swift adapter runner and actual target tooling. The Swift 6.4 knowledge baseline does not mean the adapter automatically installs 6.4. Target CI, trusted sources, actual identity, and full lifecycle gates require real adoption and validation.

## Evidence and Release Scope

Phase reports retain their fixed versions, original failures/retries, independent reviews, and limits. The 152 cases include desk decisions and scoped real isolated execution, not 152 production end-to-end tests. The final candidate requires current four repository checks/236 tests, independent documentation review, PR/main checks, and actual artifact verification. Release evidence records final commands, SHAs, and downloads; these notes do not predeclare future results.

Preparation uses existing Python 3.14 and pinned dependencies, with no production runtime/data migration. Historical canaries do not establish current platform validation. The user's explicit request authorizes this repository's new version tag/Release/assets. Identity changes require revalidation; published tags/assets are not moved or overwritten.

## Adoption, Operations, and Recovery

Merge knowledge entry points under the adoption rules, then run actual project checks and independent acceptance. Upgrade automation through a separate PR. Repository maintainers receive download/digest/extraction/installation/record-compatibility reports; no continuous on-call or automatic notification is promised. The current executor verifies the published Release, tag/source, and downloaded assets before claiming success.

Stop publication on blockers and retain evidence. After publication, preserve old tags/assets, identify affected scope, and issue a forward fix or authorized withdrawal notice. Adopters recover using their installation records/Git history; automatic downgrade is unsupported. No target cloud/store deployment or external notification.
