# Harness P0 规范落实计划

## 目标与当前状态

把现有强制要求连接到可执行入口、检查、责任和当前版本证据，确保目标项目能够判断哪些要求已落实、哪些仍阻塞。保留[三层责任边界](project-boundaries.md)及现有 docs/workflows、skills、templates 组织。

本文件是实施计划，不新增已生效规范。P0-01 已交付来源清单和执行映射，其余工作包待实施；计划交付通过不代表 P0 实施完成、目标项目已经采用或远端门禁已经启用。实施进度只在本文工作包表维护；后续 PR/Issue 链接提供执行事实，不复制另一份任务状态。

## 范围与依据

P0 包含规范落实矩阵、目标项目采用与加载验收、门禁与例外边界、证据与独立评审可信来源。P1 的领域专项扩展、运行指标体系和渠道部署适配另行规划；P0 中发现的既有强制要求缺口仍必须记录并处理，不能仅因其涉及 P1 领域而忽略。

盘点范围包括仓库 [AGENTS](../AGENTS.md)、[生命周期基线](software-development-lifecycle.md)、[编码规范](coding-standards.md)及其语言参考、[分支规范](git-branch-workflow.md)、[GitHub 默认治理](github-repository-defaults.md)、[文档规范](documentation-standard.md)、[内容治理](content-governance.md)、八阶段 workflow、其路由的 SKILL 与 references、[交付追溯契约](../templates/delivery/README.md)、适用模板、[自动化契约](github-lifecycle-automation.md)、[版本兼容](version-compatibility.md)和[升级规则](../UPGRADING.md)。重复条款引用唯一规则来源，局部约束单独登记；建议性条款与强制条款分开。

本轮不自动部署、合并或发布；用户已明确指定 anzihenry/software-engineering-canary 为真实试点，设置操作仍先审查差异且不放宽既有保护，不安装新生产依赖，不扩张现有安装器的第一层分发范围，不创建全部目标项目目录，也不批量迁移历史资产。未来确需改变机器契约或分发范围时，按既有版本、manifest 和独立验收要求单独审查。

## 工作包与顺序

| 工作包 | 责任角色 | 当前状态 | 依赖 | 主要交付物 |
| --- | --- | --- | --- | --- |
| P0-01 规范落实矩阵 | process-owner，各规范 owner 核对 | 已实现；验收见本步交付记录 | 固定盘点版本 | 强制要求清单、执行映射、缺口与完成标准 |
| P0-02 门禁与例外边界 | quality-lead、release-manager | 待实施 | P0-01 | 节点决策表、例外边界及相邻资产更新 |
| P0-03 证据与可信独立评审 | quality-lead，平台维护者 | 待实施 | P0-01、P0-02 | 证据契约、可信来源接入方案及失效验证 |
| P0-04 项目采用与加载验收 | implementation-lead，目标项目负责人 | 待实施 | P0-01 至 P0-03 | 采用清单、实际行为验证、试点验收记录 |

按依赖顺序交付，每个工作包形成可独立评审的变更。采用场景与试点条件可在 P0-01 阶段调研；完整采用验收等待前三项契约稳定。不承诺固定日历日期；盘点后依据缺口规模和目标环境确定排期。

## P0-01：规范落实矩阵

### 实施动作

1. 固定仓库完整 commit SHA，逐文件读取盘点范围，提取“必须、不得”及等价强制表达；记录原条款位置、适用条件和依赖，不只搜索关键词。
2. 分配稳定要求 ID，保留拆分、替代和退役关系。正文仍由原规范维护，矩阵只保存摘要和引用。
3. 将每项要求连接到入口/workflow/SKILL、实际执行者、工具或独立判断、失败动作、证据和验收用例。工具存在不能直接标记目标项目已生效。
4. 对无执行路径、路由断裂、证据不足或规则冲突的项登记责任人、处置任务及完成标准；经 owner 核对后决定实现、澄清适用范围或通过正式规范变更退役。

### 交付与验收

拟在 docs 保存中文落实矩阵或其导航，机器清单仅在需要确定性检查时引入。字段至少包含要求 ID、固定来源/章节、强制性、适用条件、生命周期节点、执行资产/责任角色、检查方式、失败后果、证据要求、落实状态、缺口关联和正反例验收。

分别记录 harness 能力状态（已定义、可执行、已验收）与目标项目采用状态（未接入、已接入待验证、已验证生效、不适用及理由），不得合并成一个“完成”字段。

独立评审逐文件核对提取完整性与映射正确性；全部适用强制条款有执行路径或明确缺口，全部缺口有 owner 和完成条件。矩阵盘点通过允许存在公开的待实现项，但这些项未关闭前，不报告全部规范已落实。规范或执行资产变化时同步维护映射。

## P0-02：门禁与例外边界

### 实施动作

1. 对齐本地自测、进入评审、合入、专题完成、候选验收、生产决策、批次推进和发布收口的输入、决策人、必需证据及失败动作。
2. 区分单项检查结果、总体就绪结论与执行授权；未执行不是通过，授权也不能把失败结果改写成成功。
3. 核对通用验证矩阵的“有条件通过”、workflow 的豁免条款、合入就绪与文档不可豁免要求，明确它们各自适用的范围，消除歧义。
4. 在原规范中维护权威边界，决策表和技能通过引用消费；同步受影响的 workflow、SKILL、模板及导航。

### 交付与验收

节点决策表明确通过、失败、未执行、阻塞、需重验、不适用和允许的条件性结论分别能推进到哪里。例外记录包含规则依据、授权人、范围、原因、剩余风险、到期时间、补救任务、撤销与复核条件。

保留本次必需文档、翻译、证据、独立性及既有必过 CI 的不可豁免边界；不由 Agent 自批高风险例外或生产 Go/No-Go。紧急恢复可以按既有授权执行，缺失验收仍记未完成，不能借恢复成功关闭未完成交付。

至少验收：必需 CI 失败、必需译文缺失、无授权的条件通过、已过期例外、正常授权且规则允许的例外、紧急恢复后的补验。测试验证实际结论及推进范围，不只检查表格字段。

## P0-03：证据与可信独立评审

### 实施动作

1. 复用现有追溯字段及[文档 check/snapshot/gate](documentation-tooling.md)，定义跨自测、CI、评审和候选的最小公共证据契约，不重写已有 schema。
2. 证据记录实际对象、完整提交/文件摘要、基线、环境、方法与范围、执行时间、结果、原始报告位置、来源身份及适用限制；建立要求 ID 到证据的引用。
3. 明确 head SHA、PR 合并候选、制品摘要和部署身份的对应关系。定义哪些实现、配置、依赖、环境或目标基线变化使结论失效，何时可复用未受影响范围的证据。
4. 为独立评审设计可落地的可信记录来源：核验真实作者与评审者、独立上下文、读取范围、问题及修正复核、候选快照、实际 CI 状态和受控获取方式。作者可改写的 passed 文件不是可信批准。
5. 先在受控本地环境验证一致性，再选择受信维护者或受控 CI/评审服务的接入方式。只有实际运行与身份/权限来源得到验证，才声明该项目远端强制生效。

### 交付与验收

交付中文证据与信任边界说明、适用的记录模板和试点接入方案；新增或改变目标项目正式输出模板时提供中英版本。必需工具变更使用项目编码规范、行为测试和独立验证，不自动引入新平台依赖。

至少验收：真实独立评审通过；自评、漏读必需范围、旧 SHA/摘要、作者可改写的批准、缺失原始报告、伪造或未完成的 CI 状态、合并候选不匹配被拒绝；修正后可重新验证。机械检查只保证一致性，身份和执行真实性由受控来源及实际评审保障，记录其能力边界。

若可信来源尚不可用，输出明确 blocker、负责人及解阻动作，保持缺评审即阻塞；不能以本地 gate 通过替代远端验证。

## P0-04：目标项目采用与加载验收

### 实施动作

1. 复用项目 AGENTS 模板、文档采用配置、已有安装器和 bootstrap/doctor 路径，形成统一采用清单。优先扩充已有职责；只有发现独立且重复的场景才新建 SKILL。
2. 固定 harness 来源、资产路径与版本，合并而非覆盖项目入口；填写真实检查命令、责任映射、任务事实来源、独立评审位置及适用范围。
3. 核对全局/项目/目录覆盖、技能可发现性、规范与 references 可访问性、项目工具链和实际命令；通过真实 Agent 任务观察是否读到相关规则并执行正确动作，不能只采信“已加载”的自述。
4. 建立隔离临时项目验证本地完整路径。远端试点另确认目标仓库、权限和可信评审来源；选定后使用 gh 及现有工具执行已获授权的操作，不擅自创建或修改外部项目。
5. 在试点执行正常交付和反例，形成加载、任务分支、自测、文档、独立评审、CI、受保护合入及收口的证据链。远端设置必须回读，必过门禁必须验证确实拒绝违规候选。

### 交付与验收

交付采用操作说明、采用记录模板及试点验收报告。区分新项目、已有成熟项目、非 GitHub/离线场景；不适用须有事实依据，缺权限或缺工具不能被标记不适用来制造成功。

至少验收：正常采用、缺必需技能/规范、局部入口覆盖、项目命令不可执行、缺译文、旧评审、必过检查失败、远端治理漂移；未知高风险与工具不可用时给出阻塞而非完成。

临时项目本地验收与真实远端验收分别出结论。临时验证不能证明所有项目采用成功；目标项目采用配置、入口、工具链或规则发生相关变化后，重验受影响范围。

## 总体验收与完成边界

P0 实施完成须同时满足：

- 盘点范围全部读取，适用强制要求全部映射且 P0 阻塞缺口关闭；确不适用或正式退役的项保留依据与独立核对。
- 四个工作包的资产、受影响路由和模板一致，机械检查及独立内容验证通过。
- 至少一个隔离项目跑通本地闭环；一个实际 GitHub 试点完成可信来源、真实 CI、远端规则和违规阻断验收。试点未具备条件时 P0 仅部分完成。
- 正反例证据绑定固定提交/摘要和环境；变更后重验，模拟证据、未执行项和限制明确标注。
- 不替代人工专业审批、生产 Go/No-Go，不弱化项目既有检查，不宣称其他项目已经生效。

计划交付、工作包完成、目标项目采用完成和正式发布分别判断。未来新增规则同时提交映射、执行方式与验收依据，定期复核资产过期、采用漂移及门禁失效。

## 风险与待决事项

| 风险/待决项 | 处理方式 | 责任角色 |
| --- | --- | --- |
| 强制要求数量和历史歧义尚未逐条盘点 | P0-01 后估算工作量，逐条记录冲突，不靠关键词统计宣称完整 | process-owner |
| 矩阵复制正文产生第二规则来源 | 仅保存稳定 ID、摘要和固定引用，规范变化同步更新 | 各规范 owner |
| 可信评审服务和远端试点未选定 | P0-03 比较可用来源，P0-04 确认仓库与权限；受阻不声称完成 | quality-lead、目标项目负责人 |
| 新门禁误阻塞或改变兼容契约 | 先隔离验证及反例；如改变 schema/manifest，提供迁移和兼容验收 | 平台维护者 |
| 资产增长增加 Agent 上下文和执行成本 | 保持按需加载，复用现有职责，记录试点误触发与实际耗时 | implementation-lead |

## 初始计划交付的文档影响与验证

初始计划交付仅新增中文 harness 实施计划并在根 README 增加入口；不新增 SKILL、不改变既有 workflow/SKILL 职责，因此 skills/README 和阶段路由无需调整。后续工作包改变职责时同步维护对应路由。

研究、产品、设计、工程实现、操作指南、目标项目专题及发布均无行为或状态变化，相关既有资产作为计划依据无需改写；planning 由本文承载，导航由 README 链接。此文件属于 harness 维护资产，不要求英文副本，不重排为目标项目 initiatives 目录。

本次交付执行仓库要求的 Ruff、格式检查、unittest 与仓库自检，检查命名、元信息、相对链接和导航；使用非作者独立 Agent 读取实际变更、依据及报告，绑定当前文件摘要快照。实际报告和评审记录保存在任务外部证据位置；任何相关修改后刷新快照并复核。检查结果由本次交付报告提供，本文不预填通过结论。

## P0-01 实施交付

已建立[规范落实矩阵](harness-requirements.md)、来源清单和覆盖检查，接入仓库自检；实际范围含 README、快速开始、规范、workflow、SKILL 与参考、模板。九领域影响：工程检查、计划和导航更新；研究/产品/设计无行为变化，目标项目指南/专题/正式发布不适用。没有新 SKILL 或职责变化，无需调整阶段路由；后续门禁与采用职责更新须同步。验收见本步外部报告、摘要和非作者独立记录，不将后续三个工作包记为完成。
