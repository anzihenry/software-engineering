# 软件研发全流程（基线 v0.1）

## 目的与适用范围

本流程定义产品想法如何变成可安全运行、可观测、可持续演进的软件。适用于新功能、缺陷修复、技术债治理、依赖升级和重构。阶段可根据变更风险精简，但不跳过合适的证据与质量门禁。

本文与阶段 workflow、SKILL、交付模板和演练共同属于[项目三层边界](project-boundaries.md)的第一层。GitHub 自动化只选择性落实其中可机械验证的规则；平台实现不得反向缩窄本流程，也不替代人工判断与责任。

## 指导准则

1. **价值优先**：每个变更都要说明为谁解决什么问题、如何判断成功。
2. **小步可逆**：优先交付小批、可观测、可回滚的变更。
3. **风险匹配证据**：测试、评审、发布控制与变更的影响范围相称。
4. **默认自动化**：能稳定验证的检查应进入 CI，人工评断留给需要责任的决策。
5. **安全与隐私内建**：不把密钥、个人数据、合规性作为发布前的补救事项。
6. **系统测量与学习**：用运行数据验证假设，使复盘结果改善流程与产品。

## 端到端流程

```text
需求与机会
  → 澄清与立项
  → 方案与计划
  → 开发与自测
  → 集成验证
  → 发布与变更管理
  → 运行与支持
  → 度量与复盘
                 └───────────────←
```

| 阶段 | 目标 | 核心交付物 | 离开条件（质量门禁） |
| --- | --- | --- | --- |
| 1. 需求与机会 | 确认问题值得解决 | 问题陈述、目标、成功指标、范围与约束 | 价值、优先级和负责人明确；不在范围的事项已记录 |
| 2. 澄清与立项 | 把需求变成可验收的交付 | 用户故事/缺陷说明、验收标准、风险分级、非功能需求 | 利益关系人对验收意义达成一致；高风险项已触发安全/合规评审 |
| 3. 方案与计划 | 选择可实施的路径 | 技术设计、数据/接口契约、测试策略、发布/回滚预案 | 架构、安全、可运维性与依赖风险被处理；工作拆分可估算 |
| 4. 开发与自测 | 实现可读、可维护的变更 | 代码、单元测试、迁移脚本、更新的文档 | 本地检查通过；变更与设计、验收标准可追溯 |
| 5. 集成验证 | 证明系统级行为正确 | PR、评审记录、CI 结果、集成/端到端/性能测试证据 | 必须检查全绿；评审意见已解决；高风险用例有对应验证 |
| 6. 发布与变更管理 | 受控地将价值交付给用户 | 发布包、变更记录、监控面板、回滚方案 | 发布责任人确认；可观测性和回滚方案就绪；需要时完成审批 |
| 7. 运行与支持 | 维持服务质量与用户信任 | SLO/SLI、告警、事故响应、证据记录、用户反馈 | 持续观察指标；异常按运行或安全/隐私专项事件流程处理 |
| 8. 度量与复盘 | 从交付中学习并改进 | 效果评估、事故复盘、改进任务 | 结论有数据支撑；行动项有责任人和截止日期 |

## 变更分级与门禁

| 级别 | 例子 | 最低要求 |
| --- | --- | --- |
| 低 | 文案、样式、无逻辑影响的配置 | 变更说明 + 相关自动检查 + 代码评审 |
| 中 | 普通功能、缺陷修复、内部接口变更 | 验收标准 + 测试证据 + CI + 评审 + 发布记录 |
| 高 | 账户/权限、支付、敏感数据、对外 API、数据迁移、核心基础设施 | 中级要求 + 设计评审 + 安全/合规评审 + 渐进发布 + 经验证的回滚方案 |

## 端到端演练

使用[端到端研发演练](exercises/README.md)定期验证本流程是否可执行。当前覆盖低风险文案、中风险跨层功能和高风险数据/权限变更；演练必须保留阶段决定和模拟证据的边界，不以填写文档代替真实项目所需的检查、审批或生产操作。

## 跨阶段责任

| 责任人 | 主要责任 |
| --- | --- |
| 产品/业务负责人 | 价值、范围、优先级、验收与效果评估 |
| 开发负责人 | 方案质量、实现、测试、文档、发布准备 |
| 评审者 | 独立审查正确性、可维护性、风险与测试充足性 |
| 平台/运维 | 可靠性、可观测性、发布受控与事故响应 |
| 安全/合规 | 高风险变更的威胁建模、审核与例外决策；安全/隐私事件的专项响应、证据与通知决策 |

## 流程如何沉淀为 SKILL 与 workflow

### SKILL 的定位

SKILL 用于固化高频、需要团队上下文的工作方法；它不替代原则或审批。每个 SKILL 应只负责一个清晰场景，并包含：触发条件、输入、产出、决策约束、检查方式与停止条件。

优先建立的 SKILL：

1. `requirements-refinement` — 产出验收标准、边界与风险分级。
2. `technical-design-review` — 评估架构、数据、接口、可靠性与安全取舍。
3. `implementation-and-self-test` — 实现变更并提供与风险匹配的测试证据。
4. `pull-request-review` — 根据变更风险进行代码与测试评审。
5. `release-readiness` — 确认发布、监控、回滚和审批已就绪。
6. `incident-review` — 以无责备方式复盘事故并追踪改进项。

### workflow 的定位

workflow 用于编排流程的人和系统操作。它应显式记录触发事件、输入、步骤、责任人、质量门禁、产出和异常处理。优先自动化的流程：

- PR 检查：格式化、静态分析、单元测试、依赖与密钥扫描。
- 发布流程：构建、发布预演、环境推进、健康检查、回滚。
- 事故流程：告警、分级、通报、缓解、复盘与行动项跟踪。

## 度量与演进

每月或每季度审视以下指标：交付周期、发布频率、变更失败率、恢复时间、缺陷逃逸率、产品成功指标及 SLO 达成率。不将指标用作个人绩效简化代理；以它们识别系统瓶颈。

新准则、SKILL 或 workflow 应经过“问题证据 → 小范围试行 → 复盘 → 版本化”的闭环。每项内容需指定所有者、生效范围和复审时间，防止流程与实践脱节。
