# 变更风险评估

判断变更需要何种证据、评审和发布控制，以匹配其影响面。此 SKILL 不替代安全、隐私、合规或架构专家的正式评审，也不批准风险例外。

## 输入

- 需求包、涉及的系统/数据/接口、非功能要求和已知依赖。
- 当前服务关键性、用户影响、已有控制措施和相关历史事件（如有）。

## 工作方式

1. 识别影响对象与故障后果：用户、收入、数据完整性、可用性、法律/合规义务、外部合作方及品牌信誉。
2. 检查高风险触发项：身份或权限、资金操作、敏感数据、对外 API/契约、不可逆数据迁移、关键基础设施、重大安全暴露或严格监管要求。命中任一项时，默认按高风险候选处理。
3. 评估影响范围、可逆性、检测能力和恢复能力。无法快速发现或恢复的变更应提高风险等级，即使预计发生概率较低。
4. 给出低、中或高的建议等级，并逐项说明证据、假设和可降低风险的控制措施；未知因素应倾向于保守处理或先补证据。
5. 将等级映射为最低门禁：
   - 低：变更说明、相关自动检查、代码评审。
   - 中：低级要求，加验收标准、测试证据、CI 和发布记录。
   - 高：中级要求，加设计评审、安全/合规评审、渐进发布及经验证的回滚方案。
6. 明确需要参与的角色、待完成的评审和不可接受的剩余风险，交由具有相应权限的负责人决定。

## 输出格式

```markdown
## 变更风险评估
- 评估对象与范围：
- 受影响对象及最坏后果：
- 高风险触发项：
- 可逆性、检测与恢复能力：
- 已知控制与剩余不确定性：
- 建议等级：低 | 中 | 高
- 判断理由：
- 必需门禁与证据：
- 需参与角色与待完成评审：
- 不可接受风险/待决事项：
```

## 停止条件

- 当建议等级、理由、必需门禁和责任方清晰时，交给范围与依赖对齐及后续设计。
- 当高风险触发项的影响无法判断时，停止降级结论，要求安全、合规、架构或运维专家补充评估。
- 不以“尚未发生事故”或“工期紧张”作为降低风险等级的理由。
