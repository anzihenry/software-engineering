# 通用编码规则

## 基线与适用范围

| 语言 | 目标基线 | 版本处理 |
| --- | --- | --- |
| TypeScript | 7.x | 新项目使用 7.x；嵌入式语言工具尚不兼容时允许按项目配置并行使用 TypeScript 6 工具链 |
| ArkTS | 项目 HarmonyOS SDK/API | ArkTS 编译器和语言能力随项目 DevEco/HarmonyOS SDK 约束；`.ets` 不按普通 TypeScript 兼容性推断 |
| Python | 3.14.x | 新代码可使用 3.14 语法；库的最低支持版本由项目配置决定 |
| Swift | 最低 6.4 | 采用 Swift 6 语言模式和严格并发；低于基线记录缺口，不静默升级；具体平台 deployment target 由项目决定 |
| Kotlin | 2.4.x | 遵循项目目标平台及 Kotlin/JVM、Android、Native 或 Multiplatform 配置 |
| Go | 1.27.x | `go.mod` 的 `go`/`toolchain` 指令是项目事实，不越级使用标准库或语法 |
| SQL | 方言中立 | 每个项目必须声明数据库产品、主版本、迁移工具和命名约定 |
| zsh | zsh 原生脚本 | shebang 和执行环境必须明确；要求 POSIX 可移植时应另写 `sh` 规范，不伪装成 zsh |
| C++ | C++20 | 构建系统的标准、编译器和 ABI 约束优先；扩展语法须有明确理由 |

## 必须遵守

- 先理解现有边界、测试和配置，再做最小、可审查的变更；无关格式化、重命名和重构另行处理。
- 让非法状态难以表达：使用语言的类型系统、不可变性、枚举/密封类型、约束和构造边界，而不是散落的运行时约定。
- 在系统边界验证不可信输入；授权、数据完整性和领域规则必须由拥有该责任的层执行。
- 明确失败语义。不得吞掉错误、伪造成功、泄露敏感上下文，或用断言/崩溃处理可预期的外部失败。
- 明确资源与并发生命周期：所有权、取消、超时、关闭、事务、锁和任务结束条件必须可追踪；不创建无界队列、任务或重试。
- 公共 API、持久数据、事件和序列化格式的兼容性必须显式评估；破坏性变化需要设计、迁移和版本策略。
- 日志、指标和追踪只记录诊断所需信息；密钥、token、完整个人数据和未脱敏载荷不得进入源码或普通日志。
- 新增依赖前确认必要性、维护状态、许可证、安全和体积/运行成本；未经任务授权不新增生产依赖。
- 测试针对行为和风险，覆盖主流程、边界、失败、权限及适用的并发/恢复；不以快照数量或覆盖率数字代替关键断言。

## 修改或评审前确认项目事实

- 明确本次目标、非目标、验收条件和受影响调用方；先读取现有实现、相关测试及最近的项目规则，区分手写源码、生成代码、第三方代码和历史兼容层。
- 从版本文件、锁文件、构建/CI 与实际工具输出确认语言、SDK、运行时、数据库方言及支持矩阵；语言参考的目标基线不能替代项目实际最低支持版本。
- 识别项目已有的格式、静态/类型分析、构建和测试命令及执行范围。单仓库多包、多 target 或跨语言任务按实际受影响范围选择命令，不只验证当前打开的文件；保留项目必过集合。
- 以现有测试、调用方和契约确认应保留的行为；已有代码写法可作为上下文，不能成为复制已知缺陷或越权行为的理由。影响正确性的未知事实先查仓库，仍未知则记录缺口并停止相关决定。

## 按变更风险选择验证

下表用于选择适用验证，不要求每次触发全部行，也不替代领域验证矩阵。项目已定义的必过检查仍须执行；专项不适用必须有变更事实和规则依据，缺工具、环境或证据不能记为不适用。

| 变更触发 | 需要回答的问题 | 适用验证与证据 |
| --- | --- | --- |
| 缺陷修复或行为分支改变 | 原问题可复现且新行为符合验收吗？ | 在可行时保留修复前复现与修复后回归；无法复现说明原因、替代证据及限制 |
| 解析、类型收窄、序列化或输入边界 | 非法、缺失和边界输入是否被正确处理？ | 合法/非法、空值、边界及错误映射测试；静态类型通过不能替代实际输入验证 |
| 公共 API、文件/事件格式或跨语言接口 | 生产者与消费者是否保持兼容？ | 契约、代表性调用方与版本兼容验证；破坏性变化关联迁移及设计决定 |
| 资源、异步或并发路径 | 失败、取消和超时后资源与状态是否正确收口？ | 正常与部分失败、取消、超时、重复/并发场景；核对所有权和任务结束证据 |
| 持久数据、事务、schema 或权限 | 不变量、迁移和拒绝路径是否真实成立？ | 对应方言/环境的集成、并发冲突、迁移/恢复及越权负例；替身不证明真实边界 |
| 性能或资源优化 | 在代表性条件下收益和行为是否都成立？ | 固定事前预算、环境、数据与比较基线；保留原始测量和正确性回归，不凭单次理想结果下结论 |
| 重构或工具/配置变化 | 行为是否保留，所有受影响目标是否仍可用？ | 公共行为回归、受影响目标构建/检查及声明的支持矩阵；不把编译通过等同于行为一致 |

测试优先断言外部行为与关键不变量，避免照抄实现或只匹配内部调用次数。mock/替身限定在明确边界；时间、随机、网络和全局状态依赖在适用时受控，不能用休眠重试掩盖竞态。对同一快照已通过的检查，只有新修改、失败或未决风险影响结果时才扩大或重跑；已有门禁要求重跑时仍执行。

## 可读性与设计

- 命名表达领域含义和单位；布尔值使用可读谓词，时间、大小、标识符避免无语义的裸整数/字符串。
- 函数保持单一抽象层；参数过多或布尔开关控制多种行为时，优先重塑 API，而不是继续堆积分支。
- 注释解释“为什么”、不变量、限制和外部约束，不复述语法。临时 workaround 写明原因、移除条件和关联事项。
- 优先组合和清晰的数据流；继承、元编程、反射、宏和动态执行仅在显著降低整体复杂度时使用。
- 不预先抽象尚未重复且边界不稳定的代码；重复少量简单代码通常优于错误的共享抽象。

## 自动化门禁

- 使用仓库固定版本的 formatter、linter、编译器/type checker 和测试工具；不要依赖全局工具产生不可复现结果。
- 新代码不得新增编译器或静态分析 warning。禁止通过扩大 ignore、关闭规则、删测或宽化类型来制造通过。
- 生成代码、vendor 和迁移产物按项目机制生成，不直接手改，除非仓库明确规定。
- 只报告实际执行且对应当前工作树的检查；无法执行时说明命令、阻塞原因、替代证据和剩余风险。
