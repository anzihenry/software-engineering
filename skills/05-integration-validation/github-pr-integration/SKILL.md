# GitHub PR 集成

用 GitHub Pull Request、Actions 和分支规则为小团队建立可负担的独立验证闭环。此 SKILL 编排已有验证能力和准确交接，不替代领域判断，不自行修改仓库规则、批准风险例外或取得合并/生产权限；实际动作按已有用户授权和项目机制执行。

分支准备、同步、误提交恢复或清理的实际执行使用 `git-branch-management`，不在本技能复制其操作规则；本技能原有 CI、设置或合入判断职责不变。

## 输入

- 当前分支与提交、目标分支、PR 或交接说明、风险等级和受影响领域。
- 本地自测证据、项目必需检查、GitHub 仓库可用功能及执行成本约束。
- 验收标准、契约/迁移说明和发布恢复预案。

## 默认治理检查

按[默认仓库治理](../../../docs/github-repository-defaults.md)核对默认分支保护和 `delete_branch_on_merge=true`。首次采用或漂移交给 `github-repository-bootstrap`，缺少可信检查先交给 `github-actions-bootstrap`；基线未验证时不报告受保护合入就绪，本技能仍不修改仓库设置。

## 分支操作要求

读取[分支规范](../../../docs/git-branch-workflow.md)，复用对应任务分支；提交和推送只针对该分支，按分支是否发布/共用选择同步策略，保留未提交和未推送工作。发现默认分支误提交先按规范恢复。合入后核对远端实际删除、Squash 后内容、待保留提交和其他 worktree，再按已有授权清理；本技能不因加载获得合并权限。

## 运行模型

1. **确定团队模式**：独立开发者仓库不要求无法满足的自我批准；以全新上下文的 Agent 评审作为独立审查证据，但不冒充 GitHub 人工批准。存在另一位维护者时，中高风险变更优先要求其批准。高风险变更始终保留明确的人类 Go/No-Go。
2. **创建 Draft PR**：确认变更只包含一个可回退切片，填写目的、范围/非目标、风险、验证、迁移和发布恢复信息；记录当前 head SHA，未完成验证时保持 Draft。
3. **执行稳定门禁**：GitHub Actions 应对每个 PR 启动，并始终报告一个名称稳定的必需汇总检查。格式、静态/类型分析、单元测试、构建及适用的依赖/密钥检查失败时阻塞；通过 job 条件而非整个 workflow 的路径过滤跳过无关领域，避免必需检查永久等待。可取消被新提交取代的PR诊断运行；每次合入main后的必需端到端不可静默丢失，取消/超时保留缺口并补跑准确对象。
4. **开展独立评审**：使用 `pull-request-review` 审查当前 SHA。评审上下文不继承实现者的结论，只读取需求、设计、diff 和证据；反馈分为阻塞、待澄清、非阻塞改进和可选建议，并写明复审范围。
5. **选择验证层级**：每个 PR 执行快速、确定性的基础检查；按路径、标签和风险组合移动端、Web 前端或后端专项验证。每次功能合入均使用 `system-level-validation` 组织合入前后端到端，跨域完整路径由其汇总；不把端到端仅限高风险或跨服务变更。昂贵或依赖真实设备/凭据的检查可由标签或手动事件触发，但必需项必须在合入前留下关联当前 SHA 的结果。
6. **处理反馈和回归**：在原分支提交修复，逐项解决评审线程；只按影响范围重跑专项检查，但必需汇总检查必须基于最新 SHA 重新得出结论。实质修改后复审受影响代码，禁止沿用旧提交的批准或测试结果。
7. **确认合入就绪**：使用 `merge-readiness` 核对 PR 已退出 Draft、无冲突、必需检查通过、阻塞线程解决、领域/系统证据齐全、迁移和发布信息就绪，且所有豁免有范围、授权、到期和补救计划。
8. **交给项目合并机制**：推荐受保护的 `main` 仅允许 PR 合入，默认 squash merge，并按[分支规范](../../../docs/git-branch-workflow.md)验证远端 head branch 自动删除及本地安全清理条件。独立开发者可在结论通过后人工触发或启用 auto-merge；微型团队按规则由非最后推送者批准。仅在并发合入频繁且套餐支持时启用 merge queue，并确保 Actions 同时响应 `merge_group`。

## 正式接收与合入后收口

按[阶段05](../../../docs/workflows/05-integration-validation.md)核对04正式交接与完整检查集合；缺04必需自测退回受影响范围，既定05任务承接。Draft协作不等于实收验证，实收并实际开展才验证中。可合入后按既有明确授权执行项目合并机制，保留实际PR/head/base/合入SHA/时间；未有授权可停可合入，不伪记合入。

每次功能合入main后，针对实际main对象执行核心与本次变更端到端及本节点专项，绑定构建/数据/环境/原始结果；A/B分别关联精确合入及完整用例，B更新绿不能自动覆盖A。共用报告必须核对实际所测对象及逐项覆盖，不能免任一次必需执行；取消要补跑指定对象。已合入仍只是Git事实，合入后结果/阶段完成另记，不新造第二套变更状态。

合入后失败保全证据、限定影响、暂停失败版本发布，按授权修复/回退并重验处置后版本/数据和副作用；不在main直接修任务代码。局部隔离明确可继续无关授权工作，公共能力或影响未知扩大停止范围。回退恢复基线只收口故障，原功能未交付，记录后续修复或停止决定；修复通过才可交原功能。沿[七项06交接](../../../docs/workflows/05-integration-validation.md#输出与阶段-06-交接)交范围/版本/验证/处置/发布影响/运行准备/实际决定，06仍验候选/环境/生产权限。

## GitHub 基线

- `main` 要求 PR、必需状态检查和对话解决；禁止强推和删除，管理员旁路只用于已记录的紧急恢复。
- Required checks 使用固定名称；矩阵、路径或领域变化不应改变 ruleset 依赖的检查名。
- Actions 默认最小权限。来自 fork 或不可信分支的代码不得借 `pull_request_target` 获取写权限或生产凭据。
- 快速层目标是给每次提交及时反馈；专项、系统和真实设备层按风险触发。成本优化不能使高风险证据变成可选。
- Agent 评审、Actions 结果和人工 Go/No-Go 是不同证据，不相互冒充。

若仓库采用本手册的结构化 PR 门禁，读取[PR 生命周期策略自动化](references/lifecycle-policy-automation.md)，确认 Draft/Ready 行为、权限边界和 ruleset 启用顺序。

## 停止条件

- 合入前当前证据/规则满足才交给有授权的项目合并机制；合入后对应main必需端到端通过、问题处置及06材料齐备才记录05成功完成。失败或未执行仍保持真实已合入事实及阶段未完成。
- 必需检查、阻塞反馈、风险验证或人类 Go/No-Go 缺失时停止并给出最小解阻动作。
- 修改 ruleset、创建/发布 PR 评论、批准、合并或使用管理员旁路前，分别确认已有授权；紧急性不构成默认旁路权限。
