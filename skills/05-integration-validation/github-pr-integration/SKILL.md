# GitHub PR 集成

用 GitHub Pull Request、Actions 和分支规则为小团队建立可负担的独立验证闭环。此 SKILL 编排已有验证能力，不替代领域判断，不自行修改仓库规则、批准风险例外或执行合并。

## 输入

- 当前分支与提交、目标分支、PR 或交接说明、风险等级和受影响领域。
- 本地自测证据、项目必需检查、GitHub 仓库可用功能及执行成本约束。
- 验收标准、契约/迁移说明和发布恢复预案。

## 运行模型

1. **确定团队模式**：独立开发者仓库不要求无法满足的自我批准；以全新上下文的 Agent 评审作为独立审查证据，但不冒充 GitHub 人工批准。存在另一位维护者时，中高风险变更优先要求其批准。高风险变更始终保留明确的人类 Go/No-Go。
2. **创建 Draft PR**：确认变更只包含一个可回退切片，填写目的、范围/非目标、风险、验证、迁移和发布恢复信息；记录当前 head SHA，未完成验证时保持 Draft。
3. **执行稳定门禁**：GitHub Actions 应对每个 PR 启动，并始终报告一个名称稳定的必需汇总检查。格式、静态/类型分析、单元测试、构建及适用的依赖/密钥检查失败时阻塞；通过 job 条件而非整个 workflow 的路径过滤跳过无关领域，避免必需检查永久等待。并发运行应取消同一 PR 的旧提交任务。
4. **开展独立评审**：使用 `pull-request-review` 审查当前 SHA。评审上下文不继承实现者的结论，只读取需求、设计、diff 和证据；反馈分为阻塞、应处理、建议和问题，并写明复审范围。
5. **选择验证层级**：每个 PR 执行快速、确定性的基础检查；按路径、标签和风险组合移动端、Web 前端或后端专项验证。跨客户端、服务、数据库或外部依赖时使用 `system-level-validation`。昂贵或依赖真实设备/凭据的检查可由标签或手动事件触发，但必需项必须在合入前留下关联当前 SHA 的结果。
6. **处理反馈和回归**：在原分支提交修复，逐项解决评审线程；只按影响范围重跑专项检查，但必需汇总检查必须基于最新 SHA 重新得出结论。实质修改后复审受影响代码，禁止沿用旧提交的批准或测试结果。
7. **确认合入就绪**：使用 `merge-readiness` 核对 PR 已退出 Draft、无冲突、必需检查通过、阻塞线程解决、领域/系统证据齐全、迁移和发布信息就绪，且所有豁免有范围、授权、到期和补救计划。
8. **交给项目合并机制**：推荐受保护的 `main` 仅允许 PR 合入，默认 squash merge 并自动删除 head branch。独立开发者可在结论通过后人工触发或启用 auto-merge；微型团队按规则由非最后推送者批准。仅在并发合入频繁且套餐支持时启用 merge queue，并确保 Actions 同时响应 `merge_group`。

## GitHub 基线

- `main` 要求 PR、必需状态检查和对话解决；禁止强推和删除，管理员旁路只用于已记录的紧急恢复。
- Required checks 使用固定名称；矩阵、路径或领域变化不应改变 ruleset 依赖的检查名。
- Actions 默认最小权限。来自 fork 或不可信分支的代码不得借 `pull_request_target` 获取写权限或生产凭据。
- 快速层目标是给每次提交及时反馈；专项、系统和真实设备层按风险触发。成本优化不能使高风险证据变成可选。
- Agent 评审、Actions 结果和人工 Go/No-Go 是不同证据，不相互冒充。

## 输出格式

```markdown

- PR、head SHA、base 与风险等级：
- 团队模式与所需人工决策：
- 必需 CI 检查及状态：
- 独立评审结论与未解决项：
- 领域专项和跨系统验证：
- 修复、重跑和复审状态：
- 豁免、限制与发布注意事项：
- 合入结论：可合入 | 阻塞 | 需重跑/复审
- 下一动作与责任人：
```

## 停止条件

- 证据均对应最新 SHA 且合入条件满足时，交给仓库既有合并机制。
- 必需检查、阻塞反馈、风险验证或人类 Go/No-Go 缺失时停止并给出最小解阻动作。
- 修改 ruleset、创建/发布 PR 评论、批准、合并或使用管理员旁路前，分别确认已有授权；紧急性不构成默认旁路权限。
