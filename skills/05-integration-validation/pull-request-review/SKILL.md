# PR 评审

审查变更是否符合已确认的需求、设计和风险控制，并给出可行动的反馈。此 SKILL 不替代安全、合规或架构专项审批，也不在未审阅证据时给出通过结论。

## 输入

- PR 描述、变更内容、自测记录、本地/CI 结果及关联需求、设计和风险评估。
- 契约、迁移、发布恢复预案和项目评审规则（如适用）。

## 工作方式

1. 先确认评审独立性和当前提交：微型团队优先由未参与实现的维护者评审；独立开发者可使用不继承实现结论的全新 Agent 上下文审查需求、设计、diff 和证据，但该结果不得冒充 GitHub 人工批准。高风险变更仍需明确的人类 Go/No-Go。随后理解预期行为、风险等级和变更范围，检查 PR 是否混入无关重构、隐藏范围扩大或未说明的发布影响。
2. 以用户行为和失败模式审查正确性：边界、错误处理、权限、数据完整性、并发、兼容性、资源使用和可维护性。
3. 核对实现与契约、迁移、验证策略和恢复预案的一致性；对高风险路径重点检查负向场景、可观测性和恢复能力。
4. 评估测试是否直接证明关键风险，而不是仅检查测试数量。缺少系统级证据时转交 `system-level-validation`。
5. 将反馈按阻塞、应处理、建议或问题分类；每项指出证据、影响和所需改动。变更修订后，重新审查受影响范围。

## 输出格式

```markdown
## PR 评审结论
- 评审范围、提交与风险等级：
- 结论：批准 | 修订后复审 | 需专项评审 | 阻塞

| 分类 | 发现/问题 | 影响与证据 | 所需动作 |
| --- | --- | --- | --- |

- 已确认的测试与不足：
- 需额外系统/专项验证：
- 复审条件：
```

## 停止条件

- 当评审结论和所有阻塞/待处理事项明确时，交给作者处理或 `merge-readiness` 汇总。
- 当材料或验证证据不足时，不批准；列出缺失项。
- 评审不应因时间压力跳过高风险影响或替作者解决未验证的关键问题。
- 独立开发者无法提供第二位评审者时，应准确记录 Agent 评审和自我决策的边界，不虚构审批身份或批准状态。
