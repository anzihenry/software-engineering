# 事件复盘

在服务恢复后理解事件为何能在当时的系统条件下发生和持续，识别防止或降低重演影响的改进。此 SKILL 不延迟事件恢复以等待复盘，也不把复盘作为个人问责工具。

## 输入

- 已关闭或稳定的事件记录、时间线、影响范围、通信、处置操作和运行数据。
- 架构/依赖信息、告警、发布记录、运行手册、历史相似事件和恢复目标。

## 工作方式

1. 确认服务已恢复或事件已进入稳定处置状态，再约定复盘范围和参与角色；敏感安全/隐私信息按专项要求处理。本仓库按 [GitHub 复盘自动化契约](references/github-retrospective-automation.md)建立去重、带期限的普通事故复盘。
2. 从证据重建时间线，包括检测、分诊、沟通、缓解、恢复和用户影响；区分观察事实、当时可获得的信息与事后推断。
3. 分析技术、流程、组织、工具、依赖和防护层如何共同促成影响或延长恢复。避免用“人为失误”作为终点，继续追问系统条件。
4. 识别有效防护、缺失/失效防护、检测与恢复盲区，并提出可验证的风险降低行动。
5. 记录结论、不确定性、行动候选和需要长期治理的主题；将行动交给统一跟踪，必要时回流需求、架构或运行维护。

## 输出格式

```markdown
## 事件复盘
- 事件、影响与恢复状态：
- 复盘范围与参与角色：
- 事实时间线：
- 当时可见信号与决策背景：
- 促成因素与系统条件：
- 有效/失效的防护与恢复能力：
- 改进行动候选、风险与不确定性：
```

## 停止条件

- 当事实、系统性学习和行动候选清晰时，交给行动跟踪和流程演进。
- 证据不足时标记不确定性并补充调查，不以事后推断代替事实。
- 不将无责备原则理解为不处理制度、设计或控制缺口。
