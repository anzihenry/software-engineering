# 紧急变更管理

缩短等待和范围，不取消可追溯性、测试、恢复和人类授权。普通截止日期、功能催促或 CI 失败不构成紧急变更理由。

## 输入

- 生产事件或安全风险、严重度、受影响范围、恢复目标和事件负责人。
- 拟议最小修复、当前稳定版本、可用测试、发布/恢复机制和沟通渠道。

## 工作方式

1. 记录紧急原因、用户影响、事件/安全记录、授权人和为什么标准流程来不及；明确成功、暂停和恢复判据。
2. 将变更限制为直接缓解影响的最小切片。使用 hotfix 分支和 PR 保留 diff、讨论与提交历史；除 GitHub 或仓库机制不可用且获得明确紧急授权外，不直接推送受保护分支。
3. 执行不可省略的最低检查：目标构建、相关静态检查、修复场景、关键回归、权限/数据风险及恢复步骤。无法执行的检查必须记录影响和发布后补验计划。
4. 由全新上下文 Agent 或可用维护者快速独立审查；生产动作仍由人类事件/发布负责人明确 Go/No-Go，Agent 不批准旁路。
5. 准备新的可追溯候选并仅部署到必要范围；立即观察预设健康指标。失败时停止并使用 `release-recovery-execution`，不在生产现场叠加未评审改动。
6. 缓解后把 hotfix 合回主线、恢复标准分支与版本关系，补齐完整测试、Release notes、豁免/旁路记录和短周期复盘行动。

## 输出格式

```markdown
## 紧急变更记录
- 事件/安全记录、严重度与紧急理由：
- 最小变更、source SHA、版本与影响范围：
- 已执行最低检查、独立评审与缺口：
- 人类授权、旁路及限制：
- 部署、健康与恢复状态：
- 主线同步、补验、沟通和复盘计划：
- 结论：Go | No-Go | 已缓解 | 已恢复 | 转入事故响应
```

## 停止条件

- 变更不是为了缓解当前严重影响，或缺少事件记录和生产授权时，退回标准发布流程。
- 最低构建、目标验证、恢复能力或观测缺失且风险不可接受时 No-Go。
- 用户影响缓解后立即停止紧急通道扩展，剩余改进按正常 PR 和发布流程处理。
