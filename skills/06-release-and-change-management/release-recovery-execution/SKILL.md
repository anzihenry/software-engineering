# 发布恢复执行

以最小、已预演且可观测的步骤控制发布影响。此 SKILL 不自行选择破坏性恢复路径，不把“回滚部署成功”当作数据和用户体验已经恢复。

## 输入

- 发布健康判定、当前版本/批次/范围、异常证据和事件状态。
- 已授权恢复预案、目标稳定版本或前滚候选、数据/配置/开关状态及验证方法。

## 工作方式

1. 确认暂停扩大发布，记录 GitHub deployment/run、当前制品摘要、环境、用户影响和授权人；风险快速扩大时同步转入事件响应。
2. 按预案选择最小恢复路径：关闭特性开关、恢复旧配置、回滚至已知制品、停止/补偿迁移，或部署已验证的前滚修复。涉及数据丢失、不可逆迁移或扩大权限时必须再次取得明确授权。
3. 一次只执行一个可验证步骤，使用生产 concurrency 避免其他部署交叉；记录操作者、时间、输入版本、命令/工作流和实际结果。
4. 验证应用版本、配置、数据不变量、关键用户路径和健康指标，不仅检查部署 job 状态。恢复不足时保持暂停并升级，不盲目重复。
5. 对移动/商店发布，若旧版本无法即时恢复，优先服务端兼容、远程开关、停止分阶段发布和前滚修复，并准确记录仍受影响的已安装范围。
6. 稳定后更新 deployment/事件状态，保留失败证据，并把结果交给 `release-closure` 或事故复盘。

## 输出格式

```markdown
## 发布恢复记录
- 触发条件、用户影响与授权：
- 起始版本/制品/范围与恢复目标：
| 时间 | 恢复步骤 | GitHub run/deployment | 结果 | 验证证据 |
| --- | --- | --- | --- | --- |

- 数据、配置、开关和兼容状态：
- 当前健康与剩余影响：
- 结论：已恢复 | 部分恢复 | 前滚中 | 阻塞 | 转入事故响应
- 后续动作与责任人：
```

## 停止条件

- 用户影响受控且关键健康信号恢复后，交给发布收口和运行观察。
- 预案不适用、授权不足、数据风险不明或恢复步骤连续失败时停止操作并升级事件负责人。
- 不擅自删除数据、覆盖制品、移动标签或使用管理员旁路。
