# 问题界定

将机会记录变成对“为什么做、为谁做、如何验证”的共同理解。此 SKILL 不设计实现方案，也不把缺乏证据的假设写成结论。

## 输入

- 由 `opportunity-intake` 产生的机会记录及其来源证据。
- 可用的用户研究、业务目标、运行数据、反馈、约束和已知依赖。

## 工作方式

1. 明确受影响的用户、客户、内部角色或系统，并描述其当前情境和受阻行为。
2. 用问题而非解决方案表述核心矛盾；若输入预设了方案，分离其背后的问题与该方案的假设。
3. 区分事实、假设和未知项；为关键未知项提出最小的验证方式，例如访谈、数据切分、日志分析或可控试验。
4. 定义期望结果及其衡量方式：成功指标、当前基线（若有）、目标方向、观察窗口和可能的负面护栏指标。
5. 设定范围、非目标、约束和依赖；特别记录安全、隐私、合规、性能、可靠性、预算和时间约束。
6. 判断是否足以进入下一阶段：若目标、成功判据或关键约束尚不明确，输出研究/澄清建议而非伪造精确需求。

## 输出格式

```markdown
## 问题框架
- 机会记录：
- 目标用户/受影响对象：
- 当前情境与证据：
- 核心问题：
- 期望结果：
- 成功指标：指标、基线、目标方向、观察窗口
- 护栏指标（如适用）：
- 范围：
- 非目标：
- 约束与依赖：
- 事实、假设与未知项：
- 风险与需参与角色：
- 建议：进入澄清与立项 | 先研究/补充证据 | 关闭/延后
```

## 停止条件

- 当问题、受影响对象、成功判据、范围和关键约束已清楚时，交给澄清与立项流程。
- 当关键未知项会改变是否投入的结论时，停止细化需求，先输出验证计划。
- 当问题缺乏足够价值或无法定义合理的成功判据时，建议延后或关闭，并保留证据。
