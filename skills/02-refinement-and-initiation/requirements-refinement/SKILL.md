# 需求细化

将已经界定的问题转为能够被开发、测试和业务共同理解的需求包。此 SKILL 描述预期结果，不设计技术实现，也不替代业务负责人确认范围。

## 输入

- 问题框架：受影响对象、核心问题、期望结果、成功/护栏指标、范围、约束和证据。
- 已知的用户旅程、业务规则、数据政策、现有能力及相关反馈。

## 工作方式

1. 以用户或系统行为为单位拆分最小交付项；每项应能独立产生价值或降低明确风险，避免按前端、后端等技术层机械拆分。
2. 对每项写清参与者、前置条件、触发、期望结果、失败/边界情况和不在范围内的行为。若同一规则在不同角色或状态下有差异，显式列出差异。
3. 编写可观察、可判定的验收标准。标准应描述结果而非指定内部实现；不能被合理验证的标准需回到澄清，不以模糊词替代。
4. 提取适用的非功能要求：性能、可用性、可靠性、可访问性、数据正确性/保留、审计、兼容性或本地化。没有明确需求时标注待确认，不默认“无要求”。
5. 建立追溯：每个交付项关联原问题、成功指标和已知约束；识别仍会阻塞开发、验收或发布的未知项。
6. 检查需求包是否引入了新目标或实现假设。若有，回写问题框架或列为待决决策，不静默扩展范围。

## 输出格式

```markdown
## 需求包
- 关联问题框架：
- 目标与成功指标：
- 范围与非目标：

### 交付项：<名称>
- 受影响对象与前置条件：
- 主流程/期望结果：
- 边界与失败场景：
- 验收标准：
- 非功能要求：
- 关联约束、依赖与待确认项：

- 追溯与拆分说明：
- 进入下一阶段前需确认的事项：
```

## 停止条件

- 当每个交付项具备可判定验收标准、明确边界和已标注的非功能要求时，交给风险评估与范围对齐。
- 当关键业务规则、用户对象或成功结果不明确时，停止细化，返回 `problem-framing` 或请求业务澄清。
- 不在本 SKILL 中承诺技术方案、实现工期或发布日期。
