# 需求细化

## 依据与输入

读取[阶段 02 workflow](../../../docs/workflows/02-refinement-and-initiation.md)，按其验收质量、未知分类和回流规则执行；它是完整门禁和需求状态的规则来源。接收按[阶段 01 门禁](../../../docs/workflows/01-demand-and-opportunity.md#决策门禁)批准澄清的主记录、原始来源、约束/指定方案及假设、已有业务规则和当前需求基线。不要求机会提前完成需求验收；缺上游批准可整理草案，不能写成已立项。

## 细化与判断

- 用独立需求 ID 关联机会，按完整用户/系统结果切片，明确对象、范围/非目标、角色/状态差异。保留用户指定方案作为约束；其可行性未证实就保留待验证性质，不静默替换产品或扩展目标。
- 将关键行为转成可观察结果，注明必要前置/输入/触发、预期及判断依据/方法，按适用性覆盖主流程、边界、失败、权限、取消/恢复。每项标准关联稳定要求 ID 与原始来源；不以内部步骤或“正常、友好”代替验收。
- 小任务可用清晰条目，复杂角色/状态可用表格或 Given–When–Then；不强制统一句式或所有条件量化。性能、可靠性、可访问性、数据保留/正确性、审计、兼容/本地化等按实际触发识别，保留来源、判据及验证负责人。不适用说明事实理由，缺关键阈值/业务定义继续澄清，不造数或一律留阶段 03。
- 将未知按 workflow 分类。业务/范围/验收含义缺口留阶段 02，列决策人和解阻动作；价值/用户/优先级变化才回阶段 01。已明确需求的技术未知可带验证目标/判断、负责人、探索/退出边界及失败动作交阶段 03；非阻塞细节限定调整边界与确认节点。高风险影响未知先交适用专业评估，不能改名绕过。

## 输出与交接

在一份[需求与风险包](../../../templates/delivery/requirements-risk-package.md)或现有 Issue 中更新范围、行为/NFR验收、追溯及缺口。复用已有有效材料，不另建状态或重复三份表。按需要调用 `change-risk-assessment` 处理风险、`delivery-scope-alignment` 对齐依赖/有权决定；范围和验收清楚不等于七项全部通过。

按[文档规范](../../../docs/documentation-standard.md)调用 `documentation-maintenance` 列初步文件影响及目标项目双语要求，生效业务事实回写 product，过程留原需求记录。缺口给最低解阻动作，不能以技术方案、工期或发布日期代替业务确认；本技能不批准设计投入或开发承诺。
