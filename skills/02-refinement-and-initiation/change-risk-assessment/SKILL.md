# 变更风险评估

## 依据与输入

读取[阶段 02 workflow](../../../docs/workflows/02-refinement-and-initiation.md)和[质量门禁](../../../docs/quality-gates.md)，接收当前需求基线、系统/数据/外部契约、适用非功能要求、依赖和实际控制证据。风险等级和可进入方案资格分别判断，不能仅凭等级宣布就绪。

## 评估与控制

1. 说明影响对象及最坏后果，包括用户、收入、数据完整性、可用性、外部方和法律/合规义务；核对影响范围、可逆性、检测/恢复能力及证据局限。
2. 命中身份/权限、资金、敏感数据、对外 API/契约、数据迁移、关键基础设施、重大安全暴露或严格监管等既有高风险触发项，按高风险要求处理。数据迁移不限于不可逆迁移；具体规则更严时遵循。不能因代码少、工期紧、概率低或尚无事故降级。
3. 给出低/中/高建议、依据与未知。控制分拟议和已验证，注明验证对象/版本、原始证据和局限；计划审计/回滚不能当现有保障，高风险影响无法判断时补适用专业评估，暂停受影响推进而非给出乐观等级。
4. 保留既有最低门禁：低含变更说明、相关自动检查和代码评审；中加验收标准、测试证据、CI和发布记录；高加设计评审、安全/合规评审、渐进发布及经验证回滚。按实际项目/领域规则补全，不以清单替代原必过检查。
5. 每项必需控制/评审列适用理由、责任角色/实际负责人、完成节点、验收证据及失败停止动作。进入方案前必需评估实际完成；方案/实施/发布节点的后续验证保持待完成并交接，不要求虚构提前通过，也不能将本节点必需评估以“已进队列”放行。

## 输出与权限

在原需求主记录的风险区保留触发/后果、建议等级及理由、实际专业确认、控制/评审矩阵和剩余未知，引用来源，不创建第二份状态。交 `delivery-scope-alignment` 结合 workflow 七项判断；材料不足输出缺口、负责人和最小补证动作。

Agent 建议不替代安全/隐私/合规/架构等实际评审，不代替有权人确认高风险接受或例外。例外只按质量门禁允许范围办理，不能豁免必需文档、译文、证据、独立性、必过 CI 或高风险/生产授权；不能把未来控制当降低当前等级的事实。
