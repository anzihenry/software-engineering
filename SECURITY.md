# Security and privacy reporting

Do not open a public Issue with credentials, personal information, access tokens, restricted logs, forensic evidence, exploit details, malicious payloads, or facts that could increase harm.

## Security vulnerabilities

Use [GitHub Private Vulnerability Reporting](https://github.com/anzihenry/software-engineering/security/advisories/new) for a suspected vulnerability. Include only the minimum information needed to establish contact and reproduce safely. Repository maintainers will move investigation, evidence handling, and remediation coordination into restricted channels.

## Active security or privacy incidents

Use the team's access-restricted incident system and notify the authorized security/privacy contact through the approved private channel. A public ordinary-incident Issue may retain only the opaque restricted event ID and a sanitized service-impact status; it must not contain the underlying security, privacy, personal-data, legal, or forensic details.

If an ordinary incident later indicates a security or privacy risk, stop ordinary investigation updates, create the restricted record, and use the manual incident transition workflow to mark the public record `escalated`. The workflow intentionally ignores public decision/evidence text in this mode and records only the restricted event ID plus this policy entry point.

## Response boundary

The repository automation does not perform digital forensics, determine legal or notification obligations, publish attribution, contact affected parties, or authorize production containment. Follow the governed security/privacy incident response and evidence-preservation process for those decisions.
